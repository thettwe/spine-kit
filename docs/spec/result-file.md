## 1. Scope

The collector result file is the only object that crosses from the untrusted CI stage to the trusted one. The untrusted job produces it; the trusted job ingests it and gates on it; nothing else crosses that boundary (§7.1, §7.4 rule 3). This document fixes its path, its bytes, its vocabulary, the rules under which the collector produces it, and the rules under which the trusted stage ingests it.

In scope: path and naming · encoding and framing · the header line · body record kinds and their fields · the outcome enum and its mapping to G1, G8 and G12 · runner-qualified test ids and the parametrization roll-up · **which runners a collector invokes and how their results share one file** · the deadline the collector enforces · collector behaviour on every failure of every runner · trusted-stage ingestion, including the exact ordering of checks and the classification of every rejection · **what evidence of a trunk-defined origin buys and what its absence costs** · what a candidate can and cannot influence.

Out of scope is §12. Normative references are PLAYBOOK.md v0.19 §4.3, §5.4, §5.5, §6.2, §6.3 (G1, G6, G8, G11, G12, G15, G16), §6.7, §7.1, §7.3, §7.4, §7.5 and §11. Where this document and §11 disagree, §11 wins and the disagreement is a defect in one of them — reported in §13 and §14 rather than resolved silently.

Five constraints from the design govern everything below and are not re-argued:

- **One clock, and it is the chain (§7.5).** The file carries no timestamp, no duration and no ordinal derived from wall time. The deadline of §7.1 is enforced with a clock and *records* nothing from it beyond the fact that it expired.
- **No state (§5.4 step 6, §6.1).** The file is a cache artifact inside `.spine/cache/`. It is never committed, never a graph source, never read by a run other than the one that produced it, and nothing remembers that it existed.
- **Hash policy (§11).** Git object ids for git objects; `sha256:<hex>` only for non-git artifacts. The file names a tree and a commit by object id and the release by `sha256:`; it introduces no other hash.
- **Identity is the pair (§4.3).** A repository may run several runners, so a test id alone is not an identity. **A test is identified by `(runner, id)`**, and every rule below that used to say *id* says *pair*: uniqueness, the `B` floor, the roll-up, duplicate detection, and every gate that reads them. Where a rule genuinely is about a bare id inside one runner — the `fn` prefix test, byte-sorting within a runner — this document says so.
- **Provenance is a precondition, not an ingestion test (§7.4 rule 0, as amended 2026-08-26).** Rule 0 requires the untrusted job to be triggered from trunk's own definition, and says in the same breath that a file from a job which *cannot demonstrate* that origin is still **ingested** — it fails auto-merge precondition 2, so the landing takes a human reading and never auto-merges. Exactly one check in §8 turns on provenance and it is §8.4's, never §8.2's or §8.3's. Nothing below refuses a file for want of provider evidence.

## 2. Position in the pipeline

| | |
|---|---|
| Written by | `spine check --ci --collect` — *the collector*: the release pinned by trunk's manifest, invoked by `.spine/ci.sh` read from `origin/<trunk>` (§7.4 rules 0–2). It holds no key and signs nothing. |
| Also written by | `spine check --collect` outside `--ci`, on a developer's machine, for the solo path (§5.4, *Solo developers*). |
| Runners invoked | Every adapter the **pinned release** assigns to a language in trunk's `params.langs` (§6.7) — the *invocation set* of §7.1. Never derived from the candidate's tree, and never narrowed. |
| Bounded by | `params.timeout`, read from trunk, seconds, default `1800` — one runner invocation each (§7.1). A collector that enforces no deadline is non-conformant. |
| Read by | The trusted stage, at step 3 of the landing (§5.4). It executes no repository code; the file is its only evidence about tests. |
| Gates that read it | **G1** reads the header and the whole body. **G8** reads the `base` and `result` sections for its own clause — *a landed id `T` no longer collects or does not pass* (§6.3 G8, §4.3) — and §8.5 clause 2 allocates the finding between the two, or to **neither**, where the `base` record's `out` is `xfail` or `skipped` and the id still collects on `T`. **G15** reads `tool=`. **G11** reads `tree=` and `base=` as the base-moved test. Nothing else reads it. |
| Vocabulary also used by | **G12**. `spine check --approve` collects ids and runs the frozen ids against the restored tree (§4.3, §11 CLI); its `red` is §5's enum plus §5's absence rule, over `(runner, id)` pairs. It reads this file's *vocabulary*, never this file — §5, *G12 reads the same vocabulary*. |
| Graph effect | Populates the volatile `test.result_at {tree, base, passed}` attrs only (§6.2), on `test` nodes whose ids are `test:<runner>:<id>` (§6.2). G10 excludes those attrs from the canonical dump, so a result file can never affect reconstruction. |
| Signed? | No. Its authority is the collector's pin and the trunk-scoped trigger (§7.4 rules 0–2), never a signature. Implementations do not add one. **Where the provider supplies no evidence that the trigger was trunk-scoped, the second half of that authority is simply absent** — the file is still ingested, and auto-merge precondition 2 carries the whole of the loss (§8.1, §8.4). |
| Published? | No. §7.4 rule 4 makes publication of the **gate report** to `refs/notes/spine` mandatory on every landing; this file is not the gate report and is never published, mirrored or referenced there. What reaches the note is the report's `evidence.result_sha256` over these bytes (`gate-report.md` §5.9) — a digest, not a copy. Authority is unchanged either way: no gate reads a note, and a note is never a source. |

## 3. Path and naming

```
.spine/cache/results/<T>.jsonl
```

- `<T>` is the tree object id of the synthetic merge the untrusted job computed itself, `git merge-tree --write-tree origin/<trunk> H` (§7.4 rule 3): **lowercase hex, full length, never abbreviated** — 40 characters under `object_format: sha1`, 64 under `sha256`, as trunk's manifest records. The extension is exactly `.jsonl`. The stem carries no prefix, suffix, branch name or intent id.
- The filename stem equals the header's `tree=` value byte for byte. A file whose stem and header disagree is malformed (§8).
- **One file per `T`, covering every runner.** There is no per-runner file, no per-runner directory and no per-language suffix: a repository running pytest and vitest publishes one file whose body is their union, keyed by `(runner, id)` (§4.4). §11 fixes the path as `results/<T>.jsonl` and fixes the untrusted job's artifact to one file (§8.1); a per-runner file would need both raised, and would buy nothing a `runner` field does not already give.
- A re-verification after `base-moved` computes a new `T` and writes a new file; the earlier file is never consulted again, by this run or any other.
- `.spine/cache/` is gitignored through the `.gitignore#spine` managed region (§6.7). The file is never committed. A `.spine/cache/results/*` path that appears in a candidate's *tree* is a protected-floor hit (§7.3, `.spine/**`) and is never the file the trusted stage reads — see §8.1.
- The collector creates the directory itself, writes to a temporary file in the same directory opened `O_CREAT|O_EXCL` under a name no other process can predict, `fsync`s it, and `rename()`s it over `<T>.jsonl`, replacing any file already there. **A pre-existing file at the final path is overwritten without comment**: nothing in this design may remember that a previous attempt happened (§5.4 step 6, §12), and refusing on a path that already exists is exactly that memory — on the solo path the file lives in a working copy and survives the process, so a second `--collect` for one `T` would be refused because an earlier attempt was made. The rename is also what `O_EXCL` on the final path never bought: a reader sees either no file or a complete one.
- **The file is written once, after every runner has been reaped** (§7.1 steps 9–10). There is no append, no per-runner flush and no partial publish. A reader therefore never sees a file holding one runner's records while another is still running, and the union is atomic with the rename.
- **Where the directory lives is the isolation profile** (§7.4 rule 3). Under `profile=container` it is on the host side of the boundary and is not mounted into the container: the collector's mount of the tree under test **excludes `.spine/cache/`**, and where the runtime cannot mask a subpath, the result directory lives outside the mounted root and the file is moved to `.spine/cache/results/<T>.jsonl` after the process group is reaped. Either arrangement satisfies `profile=container`; a mounted, writable result directory does not, whatever the configuration claims. Under `profile=uid` it is mode `0700` under the collector's own uid, inside the collector's own working copy of `B` — never inside the detached checkout of `T`. Under `profile=none` there is no boundary and the design says so rather than pretending: any process in the job can write it. **One boundary serves every runner**: the profile is a property of the collector, not of an adapter, and a collector that isolates one runner and not another has achieved the weaker profile and records that. One configuration is established once and tested once, and **what licenses each of these three values is fixed in §7.1**, *The isolation boundary* — the mechanism v1 ships for `container`, the tests P1-P4 that license writing it, and the refusal that answers `uid`.
- In CI the file crosses as the untrusted job's **only artifact** (§11), preserving that exact relative path. Locally (§5.4, solo) there is no artifact: `--land` reads the path directly out of the working copy.

## 4. File format

### 4.1 Encoding and framing

- UTF-8, no BOM.
- Lines are terminated by a single LF (`U+000A`). Every line, including the last, is terminated. A CR (`U+000D`) anywhere outside a JSON string escape makes the file malformed — the same rule that keeps envelopes hashing (§5.5).
- No blank lines, no comment lines, no leading or trailing whitespace on any line, no bytes after the final LF.
- Line 1 is the **header line** (§4.2). It is not JSON.
- Every line after line 1 is one JSON text in the canonical form of §4.3, in the order fixed by §4.5. The extension is `.jsonl` and the body is JSONL: exactly one JSON value per line, no framing other than LF.
- There is no size cap and no line-length cap. Readers stream.

### 4.2 The header line

Fixed by §11. Six fields, `key=value`, separated by exactly one `U+0020`, in this order:

```
tree=<oid> base=<sha> tool=<version>+sha256:<hex64> keys_visible=<bool> profile=<profile> ids=<n>
```

| # | Key | Value grammar | Produced from |
|---|---|---|---|
| 1 | `tree` | lowercase hex object id, length per `object_format` | the `T` the untrusted job computed itself |
| 2 | `base` | lowercase hex object id, length per `object_format` | `origin/<trunk>` tip at the moment the collector read policy — for a reseal, the seal's `base=`, from which every policy read for a reseal is taken (§5.5, §13 R22, and *How the collector finds a reseal's `base=`* below) |
| 3 | `tool` | `<version>` `+` `sha256:` `<64 lowercase hex>` | the collector's **own** embedded version and artifact-list hash |
| 4 | `keys_visible` | `true` \| `false` | the key-material predicate below, over the collector's own environment and every runner's |
| 5 | `profile` | `container` \| `uid` \| `none` | the boundary the collector **achieved** — created *and* tested, by the probe of §7.1; `uid` is never written by a v1 collector (§7.1) |
| 6 | `ids` | non-negative decimal, no sign, no leading zero except `0` itself | the number of `base` records that follow — the cardinality of the set of `(runner, id)` pairs collected on `B` |

Rules:

- **The header does not change under multi-runner, and no §11 amendment is required for it.** §11 closes this line at six fields; the runner qualification lives on each record instead (§4.4), which is the smaller change and the only one available — one header line cannot name several runners without a repeated key, and *a repeated key rejects the file*. The one §11 amendment the owner's decisions do require is to the `Spine-Test` payload row, not to this line; it is stated plainly in §14.
- The field order is fixed. A header whose keys appear in any other order is malformed.
- **A repeated key rejects the file** (§11). So does a missing key, an unknown key, an empty value, a value containing `U+0020`, and any value outside its grammar.
- `<version>` is trunk's `cli.version` string verbatim: non-empty, every character in `U+0021`–`U+007E` (printable ASCII, the space already excluded by the field rule above). **No version is unrepresentable.** `tool=` needs no parse to be checked — the trusted stage constructs the expected token from trunk's manifest and compares bytes (§8.3) — and where a parse is wanted, the token splits at its **last** occurrence of the literal `+sha256:`, which is unambiguous because `<dist_hash>` is exactly 64 lowercase hex. G15 refuses no manifest on this account (§13, R14).
- `tool=` is spelled exactly as the seal's `tool=` (§11, `Spine-Seal`), so the two compare by byte equality and an auditor can read them side by side.
- The collector writes what it **is**, never what trunk pins. Copying the manifest's value would assert nothing. Equality between the two is the trusted stage's check, not the collector's (§8.3).
- `keys_visible=false` asserts that **no signing key material of any kind** was reachable from the collector process or from any process group it spawned — *every* runner invocation included: no variable named `SPINE_PIPELINE_KEY` (§11, Files and refs) nor any provider-specific pipeline-key name that `ci.md` fixes, **and** no signing agent or private key — `SSH_AUTH_SOCK`, `GPG_AGENT_INFO`, a readable `~/.ssh` or `~/.gnupg`, the set §7.1 names when it says what a sandbox strips. One assertion covers the whole job: the field is not per-runner, and a collector that strips key material for one runner and not another writes `true`. `false` is the untrusted job's answer, which runs with `permissions: contents: read` and receives no secret (§7.4 rule 0); `true` is the solo path's, where the operator's own signing key is reachable from the process tree that ran the tests. One predicate, two derived answers — which is what makes §5.4's *preconditions 1 and 2 fail by construction* a derivation rather than an assertion (§13, R11). `true` is the honest negation, and the collector writes it rather than omitting the field.
- `profile=` names the boundary the collector achieved by creating it **and testing it**, never what configuration claims (§7.4 rule 3). §7.1's P1-P4 are what license `container`; `uid` is a value no v1 collector writes, because v1 ships no mechanism for it and refuses the request instead (§7.1). `n/a` is a seal value for landings that run no suite (§11); it is never a header value, and a header carrying it is malformed.
- `ids=` counts the `base` records that follow, not the result records (§13, R2). Under several runners it counts pairs, not bare ids: a repository whose pytest and vitest suites each collect an id spelled identically contributes **two** `base` records and **two** to `ids=`. A count that disagrees with the number of `base` records present is malformed. It is **not** the truncation guard: truncation removes the `end` record, which §4.5 already makes malformed. It cross-checks the collector against itself — a collector that emitted fewer `base` records than it counted is the case nothing else catches (§9).
- **`params.timeout` is not a header field.** Its value is policy, read from trunk by anyone who wants it, and writing it here would put a duration in a file §1 forbids one in. Its expiry is recorded exactly once, as `status=runner-timeout` (§7.3).

**How the collector finds a reseal's `base=`.** PB §5.5 defines it as *"the last
valid landing below the range"*, and *valid* is G9's predicate — a verifying
seal, a recomputing `envelope=`, a fenced `blob=` that hashes. **The collector
cannot evaluate it**: PB §7.4 rule 3 gives it git objects and policy, no keyring
and no envelope verifier. So it takes the **syntactic** half — the newest
first-parent commit below the orphan tip `O` carrying a `Spine-Seal` trailer —
and that is conforming.

Where the syntactic answer differs from G9's, which takes an orphan in the range
carrying a forged seal line, the collector writes a `base=` the trusted stage
disagrees with and §8.3 step 1 answers `base-moved`. That is the **retryable**
outcome and not a wrong file ingested, which is the direction to be wrong in,
and it is why the collector is not asked to do the check it has no keys for.

### 4.3 Canonical JSON

Every body line is a JSON **object** serialized in this restricted canonical form, which is RFC 8785-compatible over the value space this file uses:

1. No whitespace anywhere outside string literals.
2. Members ordered by key, ascending, over the key's UTF-16 code units. Every key defined here is ASCII, so this is byte order.
3. Strings: `"` → `\"`, `\` → `\\`, `U+0008` → `\b`, `U+0009` → `\t`, `U+000A` → `\n`, `U+000C` → `\f`, `U+000D` → `\r`; every other code point below `U+0020` → `\u00xx` with **lowercase** hex; every other code point emitted literally as UTF-8. No other escape is produced and none is accepted.
4. No numbers, no `true`/`false`/`null`, no nested objects, no arrays. v1 record kinds contain string values only. (A future kind needing a number uses a non-negative integer with no sign, no leading zero, no fraction and no exponent.)
5. Duplicate keys within an object are malformed.

**Canonical form is required on read, not only on write.** A body line that parses as JSON but is not in canonical form is malformed. This is affordable because writer and reader are the same pinned release (§4.4, note on skew) and it is what makes the file's bytes a function of its content.

### 4.4 Record kinds

Exactly three kinds. Every record carries `t`. **Unknown `t` values, unknown keys, missing keys and unknown `out`/`status`/`runner` values are all malformed** — there is no forward-compatibility relaxation, because §7.4 rule 3 already refuses a header whose `tool=` is not the base's pin, so writer and reader are the same build by construction. `out` is a member of **both** the `base` and the `result` kind, and its admissible set differs by kind: `absent` is a legal `out` on a `base` record and an unknown value — hence malformed — on a `result` one.

**`base` — one per `(runner, id)` pair collected on `B`.**

```json
{"id":"<runner-native id>","out":"<outcome on B>","path":"<repo-relative path>","runner":"<runner token>","t":"base"}
```

- `id` — the full runner-native id as collected on a checkout of `B`, **including any parametrization suffix**. Non-empty.
- `out` — **the id's own outcome on the checkout of `B`**: one value of the closed enum of §5, or the value `absent`, which is legal on a `base` record and on no other kind. It has exactly one consumer, §8.5 clause 2's `xfail`/`skipped` carve-out, which §6.3 G1 and §6.3 G8 write over *an id's collected outcome on `B`* and which is not computable without it. How each adapter obtains it — and what it costs, which for two of the four runners is one more full suite run per landing — is `import-resolver.md` §11.1 and §11.2–§11.5.
- **`absent` means the `B` outcome run reported no terminal outcome for the pair.** The id is in the floor because the `B` *enumeration* found it; nothing said how it ended. It is not `unknown`, and the two must not be merged: `unknown` is a terminal report the adapter could not map, `absent` is no terminal report at all, and only `absent` is reachable without the runner ever having got to the id. Where an adapter's `B` enumeration and its `B` outcome run are one invocation — `vitest`, `dart-test` — `absent` is unreachable on a collection that succeeded; where they are two — `pytest`, `swift-test` — it is the fail-closed value for every id the outcome run did not reach (`import-resolver.md` §11.1).
- **`out` on a `base` record is never a pass and never evidence.** No clause of §8.5 reads it as evidence that anything passed: `B`'s outcomes are trunk's own and G1 judges `T`. The single question it answers is *was this id already `xfail` or `skipped` on trunk*, and every other value — `absent` included — answers it identically, which is what keeps §5's "`passed` is the only value that is ever a pass, in any lane, in any mode, for any gate, under any runner" true word for word. It is also why a `B` outcome run that dies mid-way is not `base-collect-failed`: it can only fail to grant an exemption, never to grant a pass (§7.3).
- `path` — the repo-relative, `/`-separated path of the file the id was collected from, **byte for byte as git stores it in `B`'s tree**. The collector maps the runner's reported path onto a tree entry and emits the tree's bytes, never the filesystem's: a macOS runner reports NFD where git stores NFC, and the `G8:<path>` a finding cites has to be the tree's spelling or it names nothing. No tree entry matches: the empty string. An id with an empty `path` can never satisfy G1's `G8:<path>` exemption, which is the fail-closed direction.
- `runner` — the token of the adapter that collected it (below). Non-empty.
- **The pair `(runner, id)` is unique across the section.** A repeated pair is malformed. The same `id` under two different `runner` values is **not** a duplicate and is not malformed — that is the case the pair exists for.
- No `fn`: the `B` floor matches on full ids within a runner, never by roll-up (§6).

**`result` — one per `(runner, id)` pair a runner reported on `T`.**

```json
{"fn":"<function id>","id":"<runner-native id>","out":"<outcome>","path":"<repo-relative path>","runner":"<runner token>","t":"result"}
```

- `id` — the full runner-native id, including parametrization suffix. Non-empty, and the pair `(runner, id)` is unique across the section. As in the `base` section, one `id` under two runners is two records and no duplicate.
- `fn` — the runner-native **function** id the parametrization rolls up to (§6). Non-empty, and **a prefix of `id`**; equal to `id` when the id is not parametrized. A `result` record whose `fn` is not a prefix of its `id` is malformed. The prefix test is within the record and therefore within one runner; `fn` is never compared across `runner` values (§6).
- `out` — one value of the closed enum of §5.
- `path` — as above, resolved against **`T`'s** tree and emitted as `T`'s bytes. May differ from the same pair's `base` record: for pytest the nodeid contains the path, so the two agree or the id itself changed, but for a runner whose ids are not path-derived, a landed id whose test function moved to another file in `T` keeps its id and changes its `path`. Neither record is rejected, and §8.5 says which one a finding cites.
- `runner` — as above, and it must equal the `runner` of the `base` record the id is being matched against; matching is on the pair, so this is definitional rather than a check.

**The `runner` token.** Fixed here as a lexical form and as a provenance rule; the *set of tokens* is `import-resolver.md`'s (§6).

- Grammar: `[a-z][a-z0-9_-]{0,31}` — one lowercase ASCII letter followed by up to 31 of lowercase letters, digits, `-` and `_`. A value outside it is malformed.
- No uppercase, so byte order and case-insensitive order coincide and two spellings of one runner cannot both exist. No `U+0020`, because §4.3's `Spine-Test` payload is `<runner>` `U+0020` `<function id>` and the function id may itself contain spaces (vitest's `>`-joined names), so the split is at the **first** space and only a space-free token makes it exact. No `U+003A` (`:`), because §6.2 spells a `test` node id `test:<runner>:<id>` and only a colon-free token makes *that* split exact.
- **The token is a constant of the collector's adapter, embedded in the pinned release.** It is never read from the runner's stream, from the repository's configuration, from `params.langs`, or from the environment. That is what puts it in §9's *cannot influence* column, and it is why a candidate that renames its test framework's binary changes nothing.

**`end` — exactly one, the last line.**

```json
{"status":"<status>","t":"end"}
```

`status` is one of the closed set in §7.3, and under several runners it is the **fold** that section defines rather than any one runner's fate. The runner's exit code and signal are deliberately not recorded: they are platform-divergent, no gate reads them, and `status` already carries every distinction the mechanism makes. **There is no per-runner status record**, and §13 R28 says why.

### 4.5 Ordering

1. Header line.
2. Every `base` record, sorted ascending by the **bytes** of `runner`, then by the **bytes** of `id`.
3. Every `result` record, sorted ascending by the bytes of `runner`, then by the bytes of `id`.
4. The `end` record.

A `base` record after a `result` record, a record after `end`, a missing `end`, a second `end`, or a section out of sort order: malformed. Byte-order sorting removes the runner's report order — which is not deterministic and would otherwise be the file's only clock — and sorting on `runner` first removes the *invocation* order of the runners themselves, which is the second clock multi-runner would otherwise introduce. The file therefore does not record, and cannot be made to record, which runner ran first.

**Determinism claim.** For a fixed `(B, T)`, a fixed collector build, a fixed invocation set, and runners that behave identically, a file whose `end.status` is `complete` is fully determined byte for byte. Since v0.19 the `base` section's bytes depend on a run over `B` as well as on an enumeration of it (§4.4, `out`), so *runners that behave identically* now carries the `B` outcome run too — the condition is unchanged in words and wider in reach, and a repository with a flaky test on trunk gets a `base` section whose `out` values are as flaky as the test. Nothing about a gate outcome moves with it: the only values §8.5 distinguishes are `xfail` and `skipped`, and the sort of §4.5 is on `runner` and `id` alone, so a changed `out` reorders nothing. Two conforming implementations produce identical files. **The claim is conditioned on `complete`**: a run the deadline kills is determined only up to where the kill fell, because how many records a hung runner emitted before it was killed is a fact about wall time. §4.5's sort still makes what *was* written canonical, and §7.3's rule makes it credit nothing — so the non-determinism is confined to the evidence a human reads, and never to a gate outcome.

## 5. The outcome vocabulary

This enum is closed and is the one other specs reference. `out` takes exactly one of:

| `out` | Meaning | G1 |
|---|---|---|
| `passed` | The runner ran the id and reported it passed, with no expected-failure marker in play. | **pass** |
| `failed` | The id ran and its assertion phase failed. | not a pass |
| `error` | The id could not run, or failed outside its assertion phase: a collection error, a setup or teardown error, an import failure. | not a pass |
| `skipped` | The id was collected and not run, by a marker, a runtime skip, or an environment condition. | not a pass |
| `xfail` | The id was declared an expected failure and did not pass. | not a pass |
| `xpass` | The id was declared an expected failure and passed. | not a pass |
| `deselected` | The id was collected and excluded before running — a selection expression, a collection hook. | not a pass |
| `unknown` | The runner reported a terminal outcome the collector's adapter does not map. | not a pass |

The enum is **runner-independent**: every adapter maps its own runner's terminal reports onto these eight and no others (§6). A runner with no notion of expected failure simply never produces `xfail` or `xpass`; that is not a gap in the enum.

**Absence is not a value — in the `result` section.** A pair with no `result` record is *absent*, and absence is not a pass. (On a `base` record absence *is* written, as the value `absent`, because a `base` record cannot be omitted: the id is in the floor whatever the `B` outcome run said about it. That value is outside this enum, it is legal on no `result` record, and no gate reads it as anything but *neither `xfail` nor `skipped`* — §4.4.) This is the fifth case §4.3 and §6.3 name — "not skipped, not xfail, not deselected, not absent". `deselected` and absent are distinguished on purpose: neither is a pass, but a `deselected` record is a *collected* id and satisfies the AC-coverage clause of §8.5 where an absent one does not, which is why §6 makes deselection a mandatory transport signal.

**The mapping, stated once:** G1 counts a pair `(R, i)` as passed **iff** the body contains exactly one `result` record with `runner == R` and `id == i` whose `out` is `passed`, **and** the `end` record's `status` is `complete`. Every other value, and absence, is not a pass. `passed` is the only value that is ever a pass, in any lane, in any mode, for any gate, under any runner.

Two consequences, stated rather than hidden:

- **`xpass` is not a pass** (§13, R4). A record whose declared polarity is "expected to fail" is not evidence that an acceptance criterion holds, whatever it did this run.
- **An `xfail` test on trunk, or a skipped one, does not block every landing, and the rule that says so is computed from this enum.** Neither `xfail` nor `skipped` is a pass, and every clause of §8.5 that asks *did this id pass* still answers no. What changed is not the enum but the **allocation**: where an id's own outcome on `B` was already `xfail` or `skipped` and it still collects on `T`, §8.5 clause 2 raises no finding for it — not G1's and not G8's — because a test trunk itself reports as expected-to-fail, or as skipped, asserts nothing on trunk and is trunk's floor as it stands rather than a regression a landing introduced (§6.3, G1's row and G8's). The datum is the `base` record's `out` (§4.4); until v0.19 the record carried none, which is why earlier versions of this section refused the exemption in terms and why §13 R16 now records the reading that replaced them. The carve-out does not reach an id that *went away*: deleting an `xfail` or a skipped test is a harness change like any other and still takes a `class=protected` `G8:<path>` review (§4.3).

**What the carve-out is worth, stated — because it is what pays for `out`.** Break-glass is available only from `tests-approved` onward, and the transition table admits it from four states none of which a quick-lane candidate ever enters (§7.6, §6; §8.7 here). So **without** the carve-out a single `xfail` or a single skipped test on trunk would block **every quick-lane and every toolkit-lifecycle landing with no override available at all** — including the toolkit upgrade that would change the rule. (A `Spine-Event: reseal` landing would be the one exception, and it is not a general exit: its own `class=protected` review admits the finding, §8.7.) The one exit would be a gated intent that deletes or fixes the test **before its approval commit**, where the harness is not yet read-only from the branch's side (§6.3 G8), under a `class=protected` `G8:<path>` review — which then satisfies G1's went-away exemption, the id having gone away. Until that intent landed, the repository could land nothing through the quick lane. Multi-runner would widen that rather than narrow it: an `xfail` or a skipped test in *any* of a repository's runners would block every landing, because one file carries them all and one `end` record governs them all. **The carve-out removes that, and it removes it exactly where it bites**: a quick-lane or toolkit-lifecycle landing has no frozen ids, so its G1 is the `B` floor alone (§8.6) — clause 2, which is the one clause the carve-out touches.

**G12 reads the same vocabulary.** `spine check --approve` produces two collections on the approval tree and one run of the frozen ids against that tree with every path under the intent's `expected` touchpoints restored to its `base=` blob (§4.3, §11 CLI). `red` for a pair ⇔ its `out ≠ "passed"` **or** it is absent from that run — §11's *an id that errors, fails to import or is not collected counts as red* is exactly this enum plus the absence rule above, and `red=k/n` is sealed into the approval forever. `--approve` is not a collector invocation: no `T` exists for it, so it writes no file at the path of §3 and the artifact rules of §8.1 do not apply, nothing crossing a trust boundary. The vocabulary is shared; the file is not. Also normative for `--approve`'s *non-deterministic test ids across two collection runs* tripwire (§4.3): the two collections are compared as the sorted **`(runner, id)` pair sets** of §4.5's `base` records — so a pair that appears under one runner in one collection and another in the next is a difference, as it should be.

## 6. Runners, test ids and the roll-up

### 6.1 Ids are runner-native and runner-qualified

Ids are **runner-native** (§7.4 rule 3, §11). Spine does not rewrite, normalize, canonicalize or shorten them, and does not invent an id scheme of its own. Since v0.19 they are also **qualified**: §4.3 says a `Spine-Test` id is "qualified by the runner that collected them, since a repository may run several (`params.langs`); the pair is the identity", and §6.2 spells a `test` node `test:<runner>:<id>`. This document carries that through to the file: every `base` and `result` record names its runner, and nothing in this file or in any gate that reads it compares a bare id across runners.

### 6.2 The invocation set

The set of runners a collector invokes for a run is a **total function of trunk's `params.langs` and the pinned release**, and of nothing else:

- `params.langs` is read from `origin/<trunk>` (§7.4 rule 1, §7.1 step 1) — never from the checkout, never from the candidate.
- The pinned release maps each language to the adapter or adapters `import-resolver.md` assigns it, each with its `runner` token.
- The collector invokes **every** member of that set, in full, with no selection argument (§7.1). A collector that skips one narrows the floor exactly as a `-k` would, and is non-conformant for the same reason.

Three consequences follow and are all fail-closed:

- **A frozen `Spine-Test` naming a runner outside the invocation set can never pass.** Its `P(R, F)` is empty, which is absence, which is not a pass, so G1 fails. There is no silent skip.
- **An AC whose only `verified_by` edges name such a runner fails §8.5 clause 3** for the same reason: nothing was collected, so nothing satisfies *≥1 `verified_by` edge with a collected id*.
- **Adding a language takes effect on the landing after the one that adds it.** `params.langs` is read from trunk, so the run that lands the change reads the old value and does not invoke the new adapter. That is §7.4 rule 1 working as designed — a candidate may change policy, and the change governs later landings — and it is the same behaviour `params.isolation` already has.

Removing a language is the direction that is *not* symmetric, and it is not fully closed. See §14, OPEN-6.

### 6.3 What every runner adapter owes

For each runner it supports, the pinned release supplies, and `import-resolver.md` specifies:

1. A stable `runner` **token** matching §4.4's grammar. It is permanent: `Spine-Test` lines carrying it are sealed into landings forever (§11, `Spine-Seal`, `freeze=`), so the token cannot be corrected by a later release without invalidating approvals that name it.
2. A **total, deterministic `id → fn`** function whose output is a prefix of its input, and which is the identity on an unparametrized id. Totality matters: every id the runner can report must have an `fn`, including ids the adapter's author did not anticipate.
3. A **total `id → path`** function producing the repo-relative, `/`-separated path the id was collected from, mapped onto a tree entry and emitted as the tree's bytes (§4.4). The empty string where no tree entry matches.
4. A **total mapping** from the runner's terminal reports onto the eight values of §5, with `unknown` as the defined home for anything unmapped.
5. A **conforming transport** (§6.6).
6. A **`B` outcome per collected id.** The adapter's `B` collection yields, for every id it puts in the floor, that id's own outcome on the checkout of `B`, mapped by obligation 4 onto §5's enum, or `absent` where the `B` outcome run reported no terminal outcome for it (§4.4). It has one consumer — §8.5 clause 2's `xfail`/`skipped` carve-out — and it is not free: for two of the four v1 runners the enumeration already comes from a full run and the outcome costs nothing, and for the other two it is a **second invocation of the runner against `B`**. `import-resolver.md` §11.1 names which is which and states the cost in the same table rather than leaving an implementer to discover it.

The **static import resolver** each language owes for G8's closure recomputation (§4.3, §6.3 G8) is the same specification's, and is *not* this file's business at all: the resolver never touches a test id and this file never touches an import. The two are named together only because both are per-language and both are recomputed by the trusted stage, so a disagreement in either rejects an approval rather than merely differing.

### 6.4 The four v1 languages, and what this document deliberately does not fix

**v1 ships four: Python, TypeScript/JavaScript, Dart and Swift** (§6.7, §12). `params.langs` is an array of them; a language absent from the list cannot be gated, and adding one is a release, not a repo setting.

**Kotlin was the fifth and is dropped** (owner, 2026-08-26). The reason is a guarantee that fails silently rather than loudly: in a mixed JVM module an oracle written in a `.java` file is invisible to a Kotlin resolver, so the freeze closure computed over such a module omits edges no gate can notice, and G8 passes an approval it should have refused while reporting nothing. Every other v1 obligation can fail loudly — a missing adapter fails the job (§7.1 step 3), a runner outside the invocation set is absence and absence is not a pass (§6.2). This one cannot, and a guarantee that fails silently cannot ship. **The same rule keeps Swift and refuses one Swift *shape*.** A target that compiles Objective-C or C-family sources alongside Swift — or a C-family target a Swift file `import`s by name — hides an oracle from a Swift resolver in exactly the same way, so `docs/spec/import-resolver.md` §7.3 makes that target `lang-unclassifiable` with reason `mixed-objc-target` rather than resolving as though those files were not there. Removal and detect-and-refuse are the two outcomes **one** rule selects between, and which one it picks turns on whether the refusal falls on the ordinary shape or the exotic one: a mixed Kotlin/Java module is the ordinary JVM shape, so refusing it would have refused the language; a Swift package that compiles C-family sources is not, so refusing it leaves the rest gatable. **Neither language ships a silent hole** — that is the invariant, and the language set is the variable. (`import-resolver.md` §7.3, §18 OPEN-1 and OPEN-2.) `kotlin` is nevertheless **reserved**: no other language may claim the string, and `gradle`, `junit` and `kotest` are reserved as `runner` tokens under §4.4's grammar for the same reason a token is permanent — a `Spine-Test` line carrying one is sealed into a landing forever (§13 R27). Nothing in this document depends on any of them, and no rule here changes shape because there are four rather than five.

**This document fixes no per-language id grammar and no `runner` token, and an implementer must not infer either from the examples here.** That is `import-resolver.md`'s job, stated explicitly so nobody splits the work by accident:

- The four languages' runners, their tokens, their `id → fn` and `id → path` functions, and their outcome mappings are specified **there**, in one place, for all four — because G8 recomputes the closure in CI and two implementations differing on one edge case reject each other's approvals rather than merely disagreeing (§6.7).
- The examples in this document use `pytest` and `vitest` because the playbook's own examples do (§4.3 spells `Spine-Test: vitest …`; §6.2 spells `test:vitest:…`). **Fixing a permanent identifier by example is not good enough**, and `import-resolver.md` must ratify both tokens explicitly rather than inherit them from a worked example.
- The known hard case is unchanged and is that spec's to close: interpolating parametrization — Jest and vitest `test.each`, and any runner that builds the parameter into the test's name — leaves no unparametrized base name, so obligation 2's prefix property must be established for it or the runner declared unsupported. This document supplies the *test* (`fn` is a prefix of `id`, checked per record, §4.4) and refuses to guess the grammar that satisfies it.

The §6.5 material below is runner-agnostic and normative here. §6.7's pytest walkthrough is **illustrative only**: it is reproduced as the worked shape of the obligations above, and where it disagrees with `import-resolver.md`, that document wins.

### 6.5 The two matches, and confusing them is the likeliest divergence

- **Frozen ids roll up, within their runner.** `Spine-Test` lines carry collected *function* ids without parametrization suffixes, qualified by the runner (§4.3, §11), so a frozen entry is a pair `(R, F)`. Let `P(R, F) = { r ∈ result records : r.runner == R and r.fn == F }`, compared by exact string equality on both members. `(R, F)` passes iff `P(R, F)` is non-empty and every member has `out == "passed"`. `P(R, F)` empty means the frozen entry is absent, which is not a pass.
- **The `B` floor does not roll up.** Section 2 holds full ids as collected, each with its runner. A `base` record `b` passes iff some `result` record has `r.runner == b.runner` **and** `r.id == b.id` and `r.out == "passed"`, by exact string equality on both.

**Parsing a `Spine-Test` line into `(R, F)`.** The payload is `<runner>` `U+0020` `<function id>`: split at the **first** `U+0020`; the token before it is `R`, and every byte after it is `F`, spaces included. The split is exact because §4.4's grammar excludes `U+0020` from a token, and it is necessary because runners such as vitest produce function ids that contain spaces. A payload with no `U+0020`, or whose first token is outside §4.4's grammar, is a malformed approval line — G13's finding, not G1's. **§11's `Spine-Test` payload row does not yet spell the runner qualifier and must be amended** (§14).

**`fn` is computed by the collector, not by the trusted stage.** The trusted stage is already language-aware — in `--ci` it runs the pinned release's import resolvers for trunk's `params.langs` to recompute the closure (§4.3, §6.3 G8) — but it is deliberately **runner**-unaware: it never parses a runner-native id, and it treats `fn` as an opaque string grouped by equality **within a `runner` value**. Keeping `fn` in the collector keeps it that way, and gives up nothing to an adversary: the id string is already candidate-influenced through the runner's stream (§9), so computing `fn` in either place reads the same untrusted input. The prefix requirement of §4.4 is the runner-agnostic check that survives. The `runner` value is the one part of the identity that is *not* candidate-influenced, which is why it is a collector constant (§4.4) and why grouping by it costs the adversary something rather than nothing.

### 6.6 The transport, and what the collector records when there is no item

The transport by which the collector obtains a runner's stream is an implementation choice, constrained: it is read over a pipe the collector holds, it is not supplied by the candidate's environment, and it preserves, per item, **four** signals — the runner-native id, the per-phase outcome, the expected-failure polarity, **and deselection**. Deselection is the fourth and is mandatory: runners commonly report it outside the per-item report (pytest through `pytest_deselected`), so a transport carrying only the first three cannot distinguish a `deselected` id from an absent one — and the two differ under §8.5 clause 3. A transport that loses any of the four is not conforming, for any runner.

**Precedence is phases plus polarity, never the transport's own outcome word.** Where a runner's own summary word disagrees with what the phases and the expected-failure marker say, the phases and the marker win. A strict expected-failure that passes is `xpass` here even where the runner itself reports it as `failed`. Both are not-a-pass, so G1 is unaffected; the file's bytes are not, so the rule is normative and applies to every adapter.

**A collection error that yields no item id** is recorded as one `error` record whose `id` and `fn` are the runner's own id for the failing collector — for pytest, the file's nodeid — and whose `path` is that file, under that runner's token. Ids from the `B` set inside that file are then absent, which is not a pass. **A whole-module skip** that is neither an item report nor a collection error — `pytest.skip(allow_module_level=True)` and its equivalents — collects nothing and errors nothing, so its ids are simply absent. That is fail-closed for G1 and undiagnosable from the file, and it stays that way: the collector records nothing it did not observe.

### 6.7 pytest — illustrative

Reproduced as the worked shape of §6.3's obligations. Normative in `import-resolver.md`, not here.

For a nodeid, split on `::`. In the final component, the parametrization suffix begins at the **first** `[` and runs to the end, and exists only if the component's last character is `]`; Python identifiers cannot contain `[`, so the split is exact and invertible. `fn` is the nodeid with that suffix removed. `path` is the component before the first `::`, resolved to repo-relative POSIX form (spine pins the runner's `testpaths`/`roots` to `C-T1` at init, so rootdir is the repo root; where it is not, the collector maps it).

```
runner = pytest
id     = tests/billing/test_invoice.py::test_AC1_totals_include_tax[zero-rate]
  fn   = tests/billing/test_invoice.py::test_AC1_totals_include_tax
  path = tests/billing/test_invoice.py

runner = pytest
id     = tests/core/test_util.py::TestRounding::test_half_even
  fn   = tests/core/test_util.py::TestRounding::test_half_even     (unparametrized: fn == id)
  path = tests/core/test_util.py
```

Outcome mapping, derived from the per-item phase reports and the expected-failure marker rather than from any one transport:

| Observation | `out` |
|---|---|
| all phases passed, no expected-failure marker | `passed` |
| all phases passed, expected-failure marker set | `xpass` |
| `call` failed, no expected-failure marker | `failed` |
| `call` failed or skipped, expected-failure marker set | `xfail` |
| skipped, no expected-failure marker | `skipped` |
| failure or exception in `setup`/`teardown`, or a collection error | `error` |
| collected, then excluded before running | `deselected` |
| any other terminal report | `unknown` |

## 7. What the collector does

### 7.1 Order of operations

1. Read policy from `origin/<trunk>`, never from the checkout: `cli.version`, `cli.dist_hash`, `params.isolation`, **`params.langs`**, **`params.timeout`**, `object_format` (§7.4 rule 1). `params.isolation` absent means `none` (§6.7); `params.timeout` absent means `1800`.
2. Verify its own bytes against the pinned artifact list (§7.4 rule 2). Mismatch: fail the job, write nothing.
3. Compute the invocation set from `params.langs` (§6.2). A language in `params.langs` the running release supports no adapter for: fail the job, write nothing — the same shape as failing its own hash check, and for the same reason, since a collector that cannot run a declared language cannot produce the floor a landing will be judged against.
4. Probe key visibility (§4.2) and hold the boolean.
5. Compute `T := git merge-tree --write-tree origin/<trunk> H`. A conflict yields no `T` and therefore no file; the collector fails the job and writes nothing. The trusted stage detects `needs-rebase` independently at step 1 of §5.4 and does not need a file to do it.
6. Establish the isolation boundary the request of step 1 names, **test it**, and record the boundary the test licensed — *The isolation boundary*, below, in full. One boundary configuration serves every runner (§3). The collector never silently upgrades the recorded profile; where the boundary cannot be had, the achieved profile is `none`, and precondition 1 of §7.4 rule 5 fails on that fact alone.
7. Check out `B`, **run the restore phase for it** (*The restore phase*, below), and collect the id set **and each id's outcome on `B`** (§4.4) **for every runner in the invocation set** — all of them, each spawned under the boundary of step 6, and **before any process has run against `T`'s content** (§7.4 rule 3). The two are one invocation for some adapters and two for others (`import-resolver.md` §11.1); every invocation of either kind is a `B` invocation and all of them precede every `T` execution, which is what keeps rule 3's property intact — the outcome run reads trunk's code on trunk's tree with no candidate process in the picture, so `out` is as far outside the candidate's reach as the id set is (§9). `T` exists as a tree object from step 5, which is what names the file; what must not yet exist is a checkout of it, or any process spawned under it. That is the property rule 3 buys: no candidate can make a landed test uncollectable. **Multi-runner sharpens this rather than relaxing it**: interleaving — collect on `B` with pytest, run pytest on `T`, then collect on `B` with vitest — would let code the candidate ran under the first runner reach the second runner's collection of the floor, which is exactly the attack rule 3 forbids. Every `B` collection precedes every `T` execution, without exception.
8. Check out `T`, detached. **Run the restore phase for it** (below) — the last phase of the run that holds the job's own network. Then, for each runner in the invocation set, spawn it as a child under the runner disposition of the boundary and read its stream over the pipe, enforcing the deadline below. Invocation order and concurrency are an implementation choice and cannot affect the file's bytes (§4.5).
9. Reap every process group.
10. Reduce each runner's stream to records, take the union, sort, fold the statuses (§7.3), and write the file by the temp-and-rename of §3.

**The isolation boundary — step 6 in full.** `params.isolation` is a **request**, read from trunk and never from the checkout (step 1). `profile=` is a **finding**: the collector writes it only where a test it performed, and could have failed, licensed it. A finding is never stronger than the request; the collector never substitutes a mechanism for a profile the request did not name; and comparing the two is the trusted stage's job, never the collector's (§4.2, §8.4).

| `profile=` | v1 mechanism | Where the result directory must be | What licenses writing it |
|---|---|---|---|
| `container` | **M1** — the only mechanism v1 ships | outside the boundary's filesystem view, on the host side (§3) | **P1 ∧ P2 ∧ P3 ∧ P4**, all four passed at step 6 |
| `uid` | **none in v1** — the request is a **refusal** (disposition 1 below), never a downgrade | mode `0700` under the collector's own uid (§3) | nothing in v1 can license it, so no v1 collector ever writes it |
| `none` | **no boundary is attempted** | anywhere in the job; any process in it can write the file (§3, §9) | nothing to test — `none` asserts the *absence* of a boundary, and an absence needs no evidence |

**M1 — the shipped mechanism.** The collector spawns each runner as a child in a new **mount**, **PID**, **IPC**, **network** and **user** namespace over an **overlay of the job's own root filesystem**, configured so that:

- **No image is pulled and none is named.** The boundary is made out of the filesystem the job already has, so the toolchains under it are the ones the job installed, and no registry, no daemon and no second policy input enters the design. `ci.md` §17 defers *"container images … and how a `profile=container` boundary is actually created"* to this document; the answer to the first half is **none**, and that is why `params` needs no image key and `.spine/ci.sh` passes the collector no isolation argument.
- **The tree under test is the only writable path that is not scratch** — the detached checkout of `T` on a `T` run, the collector's checkout of `B` on a `B` invocation — together with one private temporary directory. Everything else in the child's view is read-only.
- **`.spine/cache/` is absent from that view**: masked where the runtime can mask a subpath, and otherwise outside the mounted root, with the file moved into place after the process group is reaped (§3). Either arrangement satisfies `container`; a mounted, writable result directory does not, whatever the configuration claims — which is what P1 measures.
- **The child's uid and gid are neither the collector's nor 0**, mapped inside the user namespace and visible as such **to the host** — *M1's identity source*, below, names where that mapping comes from, because a user namespace alone cannot supply it. This is why `container` subsumes `uid` rather than sitting beside it: a contained runner is also a dropped one.
- **The runner's stdout and stderr are pipes the collector holds on the host side** (step 8). No runner stream is ever a file inside the boundary: a stream the boundary can rewrite is not evidence.
- **The runner's network namespace carries no route off the host.** It is fresh, the only interface in it the collector brings **up** is `lo`, it holds no address but loopback's, and no interface, bridge, veth pair, connected socket or file descriptor from the job's own namespace is moved into it or passed across. A runner reaches `127.0.0.1` and `::1` and nothing else — which is what **P4** measures, and which is why *the runner disposition*, below, is the configuration the probe is built from.

  **A fresh namespace is not an empty one, and P4(a) is written over the reachable set for that reason.** Where the `ipip`, `gre`, `sit` or `ip6_tunnel` modules are loaded — the default on essentially every distribution kernel, CI runner images included — the kernel instantiates a per-namespace device for each at namespace creation. Measured on Linux 6.11.11, a namespace made by nothing but `unshare(CLONE_NEWNET)` contains **ten** devices: `lo`, and `tunl0`, `gre0`, `gretap0`, `erspan0`, `ip_vti0`, `ip6_vti0`, `sit0`, `ip6tnl0`, `ip6gre0` — **every one of the ten down, loopback included** (`lo` is created with `IFF_LOOPBACK` alone, not `IFF_UP`), and the namespace carrying **no address of any family**. That second fact is why P4(a) has three clauses and not two: **a fresh namespace has no usable interface at all**, so bringing `lo` up is a step the collector performs and can fail, prerequisite 5 says so in terms — *"with a loopback device it can bring up"* — and a test written only as *nothing but loopback is up* would pass a namespace in which a runner cannot reach `127.0.0.1` either. (These flags are read **over netlink**, per the paragraph below, which is normative: an inherited `sysfs` reports the job's own loopback, up, and a `sysfs` mounted inside the namespace is not a conforming source either. The trap is the reason, and the paragraph below is the rule.) The boundary is exactly the one this bullet describes; a P4(a) written as *exactly one device* would nonetheless fail on it, on every such host, for every configuration, forever. So P4(a) is written over what a device can carry rather than over how many exist: **up**, and **addressed**. That is strictly stronger against what P4 exists to detect — a veth pair moved in, a bridge, an inherited interface — since none of those carries traffic while down and unaddressed, and a down, address-less `gre0` cannot carry any.

**M1's root — an overlay, and why not the job's root itself.** Inside the mount namespace the collector mounts an **overlay** with **no upper layer** over two **lower** layers: the job's own root filesystem, and one **empty directory on a filesystem of its own** — a `tmpfs` the collector mounts for the purpose, before the overlay. An overlay with no upper layer is read-only by construction, which is the second bullet's rule and not an exception to it — the writable tree is bind-mounted over the overlay afterwards, the private temporary directory is a `tmpfs` mounted the same way, and the child is `pivot_root`ed into the result.

**Two lower layers, and why the second cannot be an ordinary directory.** The kernel refuses an upper-less overlay that has only **one** lower layer, and it refuses a second lower layer that is **reachable through the first**. Both refusals were measured on Linux 6.11.11, as uid 0 and with no user namespace involved, so neither is the unprivileged-overlayfs case prerequisite 3 already names:

| lower set | result |
|---|---|
| a single directory | `EINVAL` — *wrong fs type, bad option, bad superblock* |
| two directories on one filesystem | mounts |
| `/` alone | `EINVAL` |
| `/` and an ordinary directory beneath it | `ELOOP` — *too many levels of symbolic links* |
| **`/` and an empty directory on a `tmpfs`** | **mounts, read-only, with a `(device, inode)` pair of its own** |

The last row is M1's root, and the last clause of it is why this paragraph is normative rather than incidental: **P3's separation limb is decided by exactly that pair**, so a collector that reaches for the obvious second layer — an empty directory made under `/` — does not get a weaker boundary, it gets `ELOOP` and `profile=none` on every host, for every configuration, forever. That is the failure shape this section already recognises twice, in P2's identity source and in this paragraph's own first sentence, and the second lower layer is the third instance of it. The layer is required to be **empty** rather than merely to exist because an overlay's lower layers are searched in order and a non-empty second layer would put files in the child's root that the job's root does not have.

Prerequisite 3 therefore includes a filesystem the collector may mount a `tmpfs` on. Where it cannot, the boundary is unavailable and disposition 2 applies like any other absence. Nothing is pulled and nothing is named: the lower layer is the filesystem the job already installed, which is the first bullet's whole claim. **This is also what makes P3 decidable rather than unpassable.** A mount namespace over the job's root *is* the job's root — `stat` on the child's `/` returns the collector's own `(device, inode)` pair, so P3's separation limb would fail on every host, for every configuration, forever. An overlay is a distinct filesystem with its own device, so the pair differs, and it differs because of something the collector built: which is what a test the collector could fail is for.

**M1's identity source — a delegated range, or a root collector.** P2 requires an identity **the host** confirms is neither `U` nor 0, and an unprivileged user namespace with no delegated subordinate range cannot supply one: it maps exactly one host uid, `U` itself, so the file P2 `stat`s comes back owned by `U` and the test fails on every host, for every configuration, forever — the same shape of dead test as P3's. v1 therefore names two arrangements and requires one of them, and does not pretend the namespace alone is enough:

1. **Delegated subordinate ids.** The host grants the collector's own uid a range in `/etc/subuid` and `/etc/subgid` and supplies `newuidmap`/`newgidmap` to write the child's `uid_map`/`gid_map` (equivalently, the collector holds `CAP_SETUID`/`CAP_SETGID` on the host). The child runs as an id inside that range, which the host sees as a real, unprivileged, non-`U` uid.
2. **A root collector that drops privilege.** Where the job runs the collector as uid 0 — the ordinary case on a container-based CI runner, where `ci.md` §7.2's untrusted job is itself already a container — `U` is 0, the collector maps the child to a fixed unprivileged id, and any non-zero id satisfies P2.

**Which of the two a host supplies never reaches the file.** Both are M1, both license `container`, neither is recorded, and the header carries no trace of the difference — so two collectors on two hosts of different arrangements write the same bytes. This is not the fallback-across-mechanisms the last paragraph of this subsection forbids: that rule is about `params.isolation`'s *named mechanism*, of which v1 ships exactly one, and M1 obtaining its id map two ways is inside M1.

**These are host prerequisites, and every absence is disposition 2.** They are stated as prerequisites rather than assumed because a host that lacks one is not a broken host — it is a host whose landings a human reads. M1 requires, all five:

| # | Prerequisite | Absent when |
|---|---|---|
| 1 | the four filesystem-and-process namespaces — mount, PID, IPC, user — creatable by this collector; the **network** namespace is prerequisite 5 | not Linux (`ci.md` §5.5 ships a Darwin target); a kernel or seccomp policy that refuses `unshare`; a nested runner that already spent them |
| 2 | an identity source — a delegated `subuid`/`subgid` range with `newuidmap`/`newgidmap`, or a collector running as uid 0 | neither present, which is the bare-metal shared runner with no `uidmap` package |
| 3 | a read-only overlay over the job's root, mountable inside the namespace, **and a filesystem the collector may mount its second, empty lower layer on** (*M1's root*, below) | unprivileged overlayfs unavailable and the collector is not root; a lower layer the kernel refuses to stack; no mount point available for the `tmpfs` the second lower layer needs |
| 4 | a filesystem the mapped id can traverse — the checkouts of `B` and `T`, and the binary the probe re-execs | the collector inherits a `0700` umask. `ci.md` §5.3 narrows `.spine/ci.sh`'s process-wide `umask 077` to `umask 022` plus an explicit `chmod 0700 "$WORK"` and `0755` on the install directory and the binary, for exactly this reason (`ci.md` §5.4 item 1) |
| 5 | a **network namespace**, creatable by this collector, with a loopback device it can bring up | a kernel or seccomp policy that refuses `CLONE_NEWNET`; a runtime that hands the child a network namespace it may not replace; a child that holds no `CAP_NET_ADMIN` even inside its own user namespace, so `lo` cannot be brought up and the runner disposition would be a namespace with no usable interface at all |

An absent prerequisite is discovered at step 6, before any repository process has run, and is **disposition 2 and not a refusal**: the collector tears down whatever it built, records `profile=none`, names which prerequisite failed on stderr, and runs the suite unisolated. It is not a failed test either, and the diagnostic says which it was — a host that cannot build the boundary and a boundary that failed P1, P2, P3 or P4 differ to the human reading the `G11` wire, even though the header field they produce is the same.

M1 needs kernel namespaces and therefore exists on Linux only — prerequisite 1. `ci.md` §5.5's platform table also ships a Darwin target, where M1 cannot be created at all; that is not a refusal but disposition 2 below.

**M1's two network dispositions.** PB §7.1 grants the untrusted stage no network for anything the candidate runs, and network in one phase only — dependency restore. (Until 2026-08-27 it granted *"an allow-listed registry proxy during dependency restore, verified against the lockfile's hashes, then none"*, which promised a filter no v1 component applied; it is narrowed to what this section enforces.) The two halves of the grant have different lifetimes, so M1 gives them **two dispositions of one boundary** — identical in mount, PID, IPC and user namespace, in root, in writable tree, in masked result directory, in mapped identity and in pipes, and differing in exactly one thing, the network namespace:

- the **restore disposition** does not unshare the network namespace and keeps the job's own. `SPINE_ALLOWED_HOSTS`, `SPINE_REGISTRY_PROXY` and the client variables `ci.md` §5.6 sets are in its environment, for whatever the host puts in front of the socket to read;
- the **runner disposition** is a fresh network namespace holding only loopback. It is what **every runner invocation** is spawned under, without exception, and it is the configuration the probe below is built from and P4 is measured against.

Exactly one phase per checkout runs in the first, everything else in the second, and which is which is fixed by the collector rather than chosen per runner: *one boundary serves every runner* (§3) reads on the runner disposition, which is the only one a runner ever sees.

**The restore phase — where dependency restore lives, now that the runner has no egress.** After each checkout and **before the first runner invocation against it**, the collector runs one restore phase for that checkout: at step 7 for `B`, at step 8 for `T`. **Two per run, never one per runner**, whatever the invocation set holds.

- **Its bytes come from `origin/<trunk>`, never from a checkout.** The collector reads `.spine/restore.sh` out of trunk — the same rule, and the same reason, as `.spine/ci.sh` itself (§7.4 rules 0–1, step 1) — and runs **those** bytes against each checkout in turn, `T`'s included. A candidate therefore cannot introduce, edit or delete the one phase that holds egress, and the script that runs against its tree is trunk's. Changing it is a protected-floor landing like any other, since `.spine/**` is floor (PB §7.3). It carries **no `files[]` record and no template**: `spine init` does not write it, `manifest.md` §6.2 requires no record for it, and a repository that needs one adds it.
- **Absent on trunk, the phase is empty**, no process runs, and the collector writes one diagnostic to stderr saying so — which is what puts the remedy in the job log of the first landing that needs it. It is not a prerequisite, not a failure and not a downgrade: a repository whose toolchains are already provisioned wants exactly this.
- **It is `sh` over those bytes, at the root of that checkout**, in the **restore disposition**, under the same mapped identity, the same read-only overlay and the same masked result directory a runner gets — so a restore phase can no more write the result file than a runner can, and P1 is measured against a configuration that differs from it only in the network. It is bounded by `params.timeout` like an invocation; on expiry the collector kills its process group and reaps it.
- **Its environment is the collector's own**, unchanged, which is what §4.2's `keys_visible` predicate already covers by its first conjunct — the phase adds no environment the predicate does not already read, and it moves no header field.
- **It is not a runner.** It is in no invocation set (§6.2), contributes no `base` record, no `result` record, no id and no `status` contribution (§7.3), and **nothing reads its exit code**. A non-zero exit is a diagnostic on stderr and the run proceeds: a restore that failed reappears as the suite that fails without it, through the status vocabulary that already exists, and a new token for it would put a value in the file for a phase the file does not describe.

**The phase is not conditioned on the profile.** Under `params.isolation: "none"`, and on the solo path where no boundary is attempted at all (§7.4), the restore phase still runs — same bytes, same source, same place in the order, same deadline — simply with no boundary around it, exactly like every runner invocation in those runs. A repository's dependencies are not a function of its isolation request, and a phase that appeared and vanished with `profile=` would make the suite that runs under `none` a different suite from the one that runs under `container`. On the solo path the bytes still come from `origin/<trunk>`, as `params.langs` and `params.timeout` already do (§7.4); a working copy with no such remote-tracking ref has no restore phase, which is the empty case above.

**What is now enforced, and what is still only declared.** The *"then none"* half of PB §7.1 is **enforced and tested**: a runner has no route off the host, and P4 refuses `profile=container` to a collector that did not manage it. The *allow-listed registry proxy* half is not, and `ci.md` §5.6's split stands unchanged for it — `.spine/ci.sh` declares `SPINE_ALLOWED_HOSTS` and configures the clients that honour a proxy, and narrowing the restore phase to that list is still a network policy, a proxy sidecar or an egress firewall the host puts in front of the socket. **PB §7.1 promises exactly this and no longer more.** The residual is one phase per checkout, running trunk-authored bytes, holding the job's own network — a named, reviewed, floor-protected path instead of every test the candidate wrote, and it sits inside the residual PB §7.4 already prices.

**The probe, and the four tests.** Establishing a boundary is not creating one. It is creating one **and passing a test the collector performs and can fail** — the property §7.4 rule 5 rests on, since a header alone proves nothing and a collector that merely *configured* a boundary has measured nothing. At step 6, before `B` or `T` is checked out and before any repository process has ever run, the collector:

1. creates the result directory (§3) and writes a **canary** into it, `O_CREAT|O_EXCL`, under a name no other process can predict, holding its bytes in memory;
2. creates a **probe boundary** from exactly the **runner disposition** M1 will use for a runner invocation, differing only in that its writable tree is an empty directory of the collector's own making;
3. runs P1, P2, P3 and P4 inside it;
4. reaps it, tears it down, and removes the canary. **No probe artifact survives step 6**, whatever the outcome: §8.1 makes the untrusted job's artifact exactly one file at exactly one path, and §3 forbids anything that remembers an earlier attempt.

`U` and `Ug` below are the collector's own real uid and gid.

| | Test | Passes iff |
|---|---|---|
| **P1** | *Containment.* By absolute path, the probe attempts four things: (a) read the canary, (b) write to it, (c) create a file at `.spine/cache/results/<T>.jsonl`, (d) remove the result directory — at whichever path the collector is actually using it, since §3 admits two arrangements for `container`. | **All four fail**, *and* the canary's bytes, read back on the host side after the probe is reaped, are unchanged. One success is a failed test: a boundary the result file can be written from is not a boundary, and this is the single relation `container` has ever asserted (§3, §7.4 rule 3). |
| **P2** | *Identity.* The probe reports its real and effective uid and gid and creates a file in its writable tree; the collector then `stat`s that file **from the host side**. | The reported ids all lie outside `{0, U, Ug}`, **and** the created file's owner as *the host* sees it is neither `U` nor 0. The host's view decides: a uid the probe reports is a claim, and an identity mapping that does not reach the host is exactly the forgery a test trusting the report would miss. |
| **P3** | *Separation.* The probe enumerates its own process table and `stat`s its root directory. | The collector's own pid is **absent** from that table, **and** the probe's root is a different `(device, inode)` pair from the collector's root. |
| **P4** | *Egress.* Two limbs. **(a)** The probe enumerates its own network interfaces, their flags and their addresses, **over netlink** (`RTM_GETLINK`, `RTM_GETADDR`) from inside the boundary. **(b)** The probe opens a TCP socket and attempts a **non-blocking** `connect(2)` to `192.0.2.1:443` — RFC 5737 TEST-NET-1, an address that is unroutable on the public internet by definition, so no packet the limb emits can ever reach a third party — and the collector bounds the attempt at **one second**. | **(a)** **loopback is `IFF_UP`**, **no interface other than loopback is `IFF_UP`**, and the namespace holds **no address of any family** other than `127.0.0.1/8` and `::1/128`; **and (b)** the connect **fails**. A connect that completes is a failed test, and a connect still pending when the bound expires is **also** a failed test: pending means a route existed. The two limbs check each other and neither alone would do. (a) is the evidence and needs no packet, but a collector could read it from the wrong namespace; (b) is answered by the kernel the child is actually in, but on a host with no default route it would pass without a namespace, and (a) catches that. |

**P4(a) is read over netlink and never over `sysfs`, and this is normative rather than an implementation note.** §12 leaves the syscall that *creates* M1's namespaces to the implementation, and this does not withdraw that; what a **test** reads is a different question, because a test that can be aimed at the wrong namespace is not a test. `unshare(2)` does not re-derive an already-mounted `sysfs`, so `/sys/class/net` inside a correctly isolated namespace continues to list the **job's own** interfaces. Measured on the same host as above, inside a namespace whose netlink view is the ten devices named there:

```
/proc/net/dev  : lo tunl0 gre0 gretap0 erspan0 ip_vti0 ip6_vti0 sit0 ip6tnl0 ip6gre0
/sys/class/net : bonding_masters erspan0 eth0 gre0 gretap0 ip6gre0 ip6tnl0 ip…
```

`eth0` is the job's external interface and it is not in the namespace. A probe reading `sysfs` therefore reports a false **fail** here, and — on a runtime that *did* re-derive it — could report a false **pass** for a namespace it never entered. A netlink socket is answered by the namespace the calling task belongs to and cannot be pointed at another, which is the property P4(a) needs and the only one that distinguishes it from a configuration claim. The per-namespace `procfs` net files (`/proc/net/dev`, `/proc/net/if_inet6`) have the same property and are a conforming source; `sysfs` is not.

**The verdict, and it is the whole of `profile=`.**

```
step 1:  params.isolation = "uid"        ->  refuse: fail the job, write nothing   (disposition 1)
step 6:  params.isolation = "container"  ->  "container"  if P1, P2, P3 and P4 all passed
                                             "none"       otherwise                (disposition 2)
         params.isolation = "none"       ->  "none", and no boundary is attempted
```

**Outside `--ci` none of this runs**: §7.4 makes the solo collector attempt no boundary, refuse nothing, and write `none`. There is no third outcome and no partial one: three tests out of four is `none`. `profile=` is not per-runner and not per-invocation — **one configuration is established and tested once**, and every invocation is spawned from that configuration, which is what §3 means by *one boundary serves every runner* and why a collector that isolates one runner and not another has achieved the weaker profile.

**Every runner invocation is spawned under it** — the `B` enumeration, the separate `B` outcome run where an adapter has one (`import-resolver.md` §11.1), and the `T` run alike (steps 7 and 8). This is why step 6 precedes step 7 rather than sitting between the two checkouts: trunk's own tests are code that runs in the job too, and a floor enumerated by an uncontained process is a floor the job's other processes had a write path to.

**When the requested profile cannot be established.** Two dispositions, and they differ because their causes do.

1. **This build ships no mechanism for the requested profile.** In v1 that is exactly `params.isolation: "uid"`. The collector **refuses**: it fails the job and writes nothing, at **step 1**, where the value is read and before `T` exists — the same shape as step 3's declared language with no adapter, and for the same reason, since a collector that cannot establish a declared boundary cannot produce the evidence a landing will be judged against. `.spine/ci.sh` already carries the consequence and needs no change: no file at the expected path is `die 2`, exit 2, *refused: nothing ran and no result file exists* (`ci.md` §5.2). **It is never a downgrade to `none`.** A build limitation is not a repository's isolation failure; no landing in that repository could ever clear it; and `none` would spend a permanently sealed field (PB §11, `Spine-Seal`) on a defect the repository can neither see nor fix, dressing a refusal as a green run that merely cannot auto-merge. The remedy is a protected-floor edit of `params.isolation` (PB §7.3), or a release that ships a `uid` mechanism — at which point this row moves and nothing else here does. **How a manifest comes to carry `uid` at all is narrow**, and deliberately so: `spine init` refuses `--isolation uid` (PB §11) and `manifest.md` §6.2 check 12b refuses `params.isolation = "uid"` outright at the landing that installs it. This disposition is the residual for a manifest that reached trunk before either existed, or around them; it is not a path a conforming toolchain opens.
2. **The mechanism is shipped and the boundary could not be had** — any of M1's five host prerequisites absent (a Darwin runner, a kernel that refuses the namespaces, no delegated `subuid` range and no root, no overlay, a filesystem the mapped id cannot traverse, no network namespace or no loopback inside one), creation failed, or any of P1, P2, P3 or P4 failed. The collector tears down whatever it built, **runs no runner inside a boundary that did not pass its test**, records `profile=none`, and proceeds with the run. The suite runs unisolated and the file says so.

   **This downgrade is never silent**, in three places at once. The header carries `none` against a manifest that says `container`, which fails auto-merge precondition 1 on that fact alone and raises the `class=tripwire` `G11` wire with a mandatory `reason=` (§8.4, §7.4 rule 5). `profile=none` is sealed into the landing and stays in the ledger for it forever (PB §11). And the collector writes a diagnostic naming which of M1's five prerequisites, or which of P1, P2, P3 and P4, failed to stderr, which `ci.md` §5.1 reserves for exactly that — *"every diagnostic, and all of the collector's own output, goes to stderr"* — and which the job log carries. What it is **not** is a refusal, and the reason is the design's rather than this document's: rule 5's answer to weak isolation is always that a human reads the landing, never that nothing happens (§8.4, §13 R9). A repository whose runner cannot hold a namespace would otherwise be unable to land at all — a strictly worse posture than landing under a human's eye, and one that would make M1's platform reach a silent product boundary.

**The collector never upgrades, and never substitutes.** Where `params.isolation` is `none` no boundary is attempted and the header says `none`; a collector that builds one anyway and writes `container` is non-conformant, because it would report a boundary trunk never requested and hand precondition 1 an agreement it was never meant to find (§8.4). Where a future release ships more than one mechanism, it attempts **only** the mechanism its request names: a fallback order across mechanisms would make the header a function of the host's inventory rather than of the request, and two collectors of the same build would then disagree on the same repository.

**What the boundary is not.** It is not the key-visibility control: `keys_visible` is a predicate over the collector's own environment *and* every runner invocation's (§4.2), so hiding key material from a contained runner does not make it `false` where the collector itself could reach it, and the two header fields are independent. It is not a defence against a lying runner either. P1, P2, P3 and P4 measure the boundary between the collector and the runner — its filesystem, its identity, its process table and its route off the host — which is the only thing `container` has ever claimed — PB §7.4 states the residual in terms: *"they isolate the collector from the runner, and nothing more."*

**The deadline.** `params.timeout` is a **strictly positive integer number of seconds**, read from trunk at step 1, defaulting to `1800` when the key is absent — the way `params.isolation` absent means `none` (§6.7). It is present and not a positive integer: the collector fails the job and writes nothing (step 1's shape). It bounds **one runner invocation**, and the `B` enumeration, the `B` outcome run and the `T` run are each an invocation. It also bounds **each of the two restore phases**, which are not invocations and are two per run whatever the invocation set holds — so the worst-case wall time is `params.timeout` times the number of invocations **plus two**, and the invocations are two or three per runner depending on the adapter (`import-resolver.md` §11.1), not one per runner. A repository declaring three languages may therefore take up to nine or ten times `params.timeout` in the worst case. This document does not add a whole-job deadline, because §6.7 fixes the field's meaning as a single invocation and a second budget would be a second policy nobody declared. **A collector that enforces no deadline is non-conformant**, whatever the manifest says: the field's absence selects the default, never the absence of the control.

On expiry the collector kills the whole process group of that invocation and reaps it; the run's `status` contribution is `runner-timeout` (§7.3), and no wall-clock quantity enters the file. The deadline covers **every** invocation, both `B` invocations included, **and both restore phases**: a hung collection, or a restore that waits forever on a socket, is the case that would otherwise wedge a job forever. A restore phase that expires is killed and reaped, contributes no `status` like any other restore outcome, and the run proceeds. Expiry during the **enumeration** of `B` kills it, the enumeration failed, and the fold of §7.3 yields `base-collect-failed` — first in table order, and the honest one, because `status` describes the body and a file with no `base` records is `base-collect-failed`'s body and not `runner-timeout`'s. Expiry during the separate **`B` outcome run**, where an adapter has one, is not that: the floor is already enumerated, so the run is killed, every id it had not reached takes `out: "absent"`, and the file's `status` is unaffected. That asymmetry is deliberate and is the fail-closed direction — an enumeration that stops early shrinks the floor, while an outcome run that stops early can only withhold exemptions (§4.4, §8.5 clause 2).

An old collector that does not know the key defaults to `1800` and therefore still enforces *a* deadline. That is the right direction: the deadline is a liveness control, never an integrity one, so a binary enforcing a laxer bound than the repository asked for burns CI minutes and credits nothing.

**The collector passes no selection, and runs every runner.** On `B` and on `T` alike it passes no selection argument of any kind — no `-k`, no `-m`, no node ids, no paths — and it invokes every member of the invocation set. Selection comes only from the runner configuration in the tree under test, whose `testpaths`/`roots` `spine init` pinned to `C-T1` (§9), which `C-T2` freezes, and against which the quick-lane router escalates any diff (§3.5). A collector that narrows the run narrows the floor, and dropping a whole runner narrows it hardest of all.

### 7.2 Reduction

- One `result` record per distinct `(runner, id)` pair. When a runner reports an id more than once — a rerun plugin, a repeated phase — **the last terminal outcome that runner reported for that id wins**. The collector transcribes; it does not adjudicate. Spine's stated position is that G1 is exactly as strong as the runner's honesty and no stronger (§7.4), and the runner's config is frozen (§4.3), so a candidate cannot install a rerun plugin mid-flight to launder a failure. The direction is fail-open and deliberate: where the repo's *own* frozen configuration reruns, a `failed` followed by a `passed` is a pass, because the repo chose that configuration under `C-T2` (§13, R6). Reduction never crosses runners: two runners reporting one id string produce two records, and neither is the other's rerun.
- `base` pairs are a set: duplicates at collection are reduced to one record, per runner.
- An id whose bytes are not valid UTF-8 is not representable. **That runner** contributes **no** `result` records at all and its status contribution is `stream-invalid`; other runners contribute theirs, and the fold of §7.3 makes the file's `status` `stream-invalid`, so nothing credits either way. Non-UTF-8 test ids are unsupported in v1 (§12).

### 7.3 When a runner crashes, times out, or produces nothing

The collector always writes a file once `T` is known and policy has been read. The header is always complete and honest. The `end` record says what happened.

Each invoked runner produces one **status contribution** from the rows below, evaluated **top to bottom, first match wins**, and contributes to the body exactly what its row's third column says. `complete` requires **both** that the adapter parsed that runner's terminal session-end event **and** that no member of its process group was terminated by a signal; a member that dies abnormally after the terminal event yields `runner-failed`. The runner's *exit code* is never the discriminator — a red suite exits non-zero on every runner that ships, so an exit-code test would make `complete` unreachable for exactly the runs G1 exists to judge, and it would readmit the platform-divergent value §4.4 keeps out of the file (§13, R23).

| `status` | Contributed when | That runner contributes |
|---|---|---|
| `complete` | The runner terminated of its own accord and its stream was parsed to a terminal event. | Its full `base` and `result` records. |
| `base-collect-failed` | The **enumeration** of the id set on the checkout of `B` failed, or its deadline expired during that enumeration. A failure of the separate `B` **outcome** run, where an adapter has one, is *not* this row (§4.4, §7.1). | **Nothing, from any runner** — see the all-or-nothing rule below. |
| `spawn-failed` | The runner could not be started at all — no runner configuration in the tree under test included. | Its `base` records; no `result` records. |
| `no-output` | The runner started and terminated but emitted no parsable stream event. | Its `base` records; no `result` records. |
| `stream-invalid` | Its stream contained an event the adapter cannot parse, or an id that is not valid UTF-8. | Its `base` records; no `result` records. |
| `runner-failed` | The runner terminated abnormally, or its stream ended mid-record. | Its `base` records; every `result` record parsed before the break. |
| `runner-timeout` | The collector's deadline expired on the `T` run and it killed that process group. | Its `base` records; every `result` record parsed before the kill. |

**The fold.** `end.status` is `complete` **iff every** invoked runner contributed `complete`. Otherwise it is the **first row in this table's order, after `complete`, contributed by any runner**. The fold is over the table's fixed order and not over invocation order or wall time, so it is deterministic and independent of which runner ran first — which §4.5's determinism claim requires.

**Collection on `B` is all-or-nothing across runners.** If *any* invoked runner's collection on `B` fails, the file's `status` is `base-collect-failed`, `ids=0`, and **no `base` and no `result` records are written at all**, from any runner. A partial `base` section is a *shrunken floor*, which is the one truncation that weakens rather than tightens the gate (§13, R13), and it would be indistinguishable from a repository that genuinely has fewer landed tests. `ids=0` here means *no `base` records follow* — the cardinality of `B`'s pair set is unknown and `status` carries that truth.

**A failed `B` outcome run is not all-or-nothing, and is not a status at all.** Where an adapter takes the floor's membership from one `B` invocation and each id's `out` from a second (`import-resolver.md` §11.1), a failure of the second — it did not start, it died, it was killed at the deadline, its stream was unparsable — leaves the `base` section whole and gives every id it did not report a terminal outcome for `out: "absent"`. No status contribution is made for it and `end.status` does not move. The two failures are not symmetric because their consequences are not: a truncated enumeration writes a floor smaller than `B`'s real one, which is the one truncation that weakens the gate (§13, R13), whereas a truncated outcome run can only fail to grant the carve-out's exemption, which leaves G1 and G8 exactly where they stood before the carve-out existed. Fail-closed in both directions, by two different rules.

Two rules make this safe:

- **`status ≠ complete` ⇒ no pair counts as passed**, whatever any `result` record says, and whichever runner produced it. Records are still written because they are evidence for the human who will read the wire; they are never credit. This closes the one place where an empty or near-empty file could pass vacuously: a quick-lane landing has no frozen ids, so its G1 is the `B` floor alone, and a `base-collect-failed` file would otherwise satisfy it by emptiness. It is also what makes the fold safe: **one hung runner fails the landing, including another runner's genuinely green suite.** That is deliberate. The cheaper alternative — credit the runners that completed and fail only the one that did not — is defensible on its own terms and is refused because it introduces partial crediting into the one artifact §13 R13 keeps whole, for a gain of precision in a finding rather than in an outcome (§13, R28).
- The collector's exit status is non-zero for every `status` other than `complete`, and for `keys_visible=true`, so the untrusted job fails as §7.4 rule 0 requires. Writing the file anyway is deliberate: a failed job that produced no file and a failed job that produced an honest one are different things, and the trusted stage should be able to say which.

**What the file does not say.** With several runners, `end.status` names *what* went wrong and not *which runner* it went wrong in. That is an accepted loss: the file is a gate input and not a report (§12), the evidence for the human is the CI log and the `spine review` packet (§6.5), and §13 R28 states the alternative that was refused and why.

### 7.4 Outside `--ci`

The solo path (§5.4) runs the same code, and two header values are settled before any observation is made: **`keys_visible=true`**, out of §4.2's own predicate, because the operator's own signing key is reachable from the process tree that ran the tests; and `profile=none`, because **outside `--ci` the collector attempts no boundary at all**. A laptop is one uid and one process tree, the operator's key is reachable from it either way, and a boundary between a collector and a runner that both answer to the same person establishes nothing the header could honestly report. So `params.isolation` is not a request the solo collector acts on: it attempts nothing, it **refuses nothing** — a manifest declaring `uid` costs a solo developer no run, and disposition 1 of §7.1 is a `--ci` rule — and it writes `none`. Preconditions 1 and 2 of §7.4 rule 5 therefore fail by construction, which is exactly what §5.4 requires and costs a solo developer nothing they had.

`params.langs` and `params.timeout` are read from trunk on the solo path too, exactly as in `--ci` (§7.4 rule 1). A solo developer's laptop does not choose its own invocation set or its own deadline, and a `--collect` run on a working copy whose manifest differs from trunk's uses trunk's.

## 8. Ingestion

The trusted stage performs these checks in this order and stops at the first failure. Ordering is normative: it is what decides whether a run is retried or refused.

### 8.1 Provenance of the bytes

The file is read from the artifact of the untrusted job this run was triggered by, and from nowhere else. **A result file from a job that cannot demonstrate a trunk-defined origin (§7.4 rule 0) is ingested**: it is checked, labelled and evaluated like any other, and the whole of the consequence is that **auto-merge precondition 2 fails** (§8.4), so the landing takes a human reading and never auto-merges. This is not one of the checks below, it is not a `result-missing` or a `result-malformed`, and it is not a reason to refuse anything.

**The strict reading is withdrawn** (owner, 2026-08-26; §13 R31). Earlier drafts of this section, and PLAYBOOK §7.4 rule 0 before its amendment of the same date, said such a file "is never ingestible". Read literally that sentence names no test the trusted stage can perform and it fails every landing on two of the three shipped providers: on GitLab with in-repository configuration and under `--ci generic` no provider fact establishes the origin, so every run would refuse its file, `result-missing` would be a G1 finding on every landing, and in the quick lane a `result-missing` G1 finding has no override at all outside a reseal (§8.7). Two providers made non-functional rather than degraded, to buy a property precondition 2 already delivers.

**Trunk-defined origin evidence, defined once.** The run has it iff, from provider facts it read **itself** — never from anything in the file, and never from the candidate — it established that the untrusted job whose artifact it is ingesting ran from a workflow definition taken from trunk. What counts as such a fact is `ci.md`'s, per provider and not this document's to invent: `ci.md` §14 R11 fixes GitHub's test (three clauses on the `workflow_run` event, the triggering workflow's **path**, and the head repository), and `ci.md` §10.3 scores every shipped arrangement — GitHub establishes it, GitLab with in-repository configuration and `--ci generic` never do. **Absent evidence and disproved evidence are one case here**, and both are precondition-2 failures: the design has no third answer, and a provider that reports nothing is exactly as far from rule 0's arrangement as one that reports the wrong thing.

Two things follow, and neither is softened:

- **The evidence is a property of the arrangement, not of the file.** It is the same answer for every run in a repository until `params.ci` or the provider's configuration changes, so it can never be bought by a candidate and never lost by one. A candidate that could turn it off could only turn its own auto-merge off, which §9 already grants it.
- **Where it is absent, the whole result file is the candidate's** (`ci.md` §10.2): `tool=`, `keys_visible=false` and `profile=container` are strings a forger copies out of trunk's manifest, and §8.3's checks pass on a forgery by construction. That is precisely why the answer is a human reading rather than a refusal — and it is why §9's *cannot influence* column is conditioned on this evidence rather than stated flat.

**What is still refused, and it is only shape.** The artifact contains **exactly one regular file, at exactly `.spine/cache/results/<T>.jsonl`** — one file however many runners the repository declares (§3). Extra entries, directories, symlinks, absolute paths and `..` components make it not-a-result. The path is the one the trusted stage **materializes** the artifact at, relative to its own workspace; how a provider names entries inside its transport container is that provider's business (`ci.md` §6.3, §14 R9). The trusted stage never reads a result file out of a repository working tree, which is what makes a `.spine/cache/results/…` path committed into a candidate's tree irrelevant as well as a floor hit.

On the solo path there is no artifact; the file is read from the working copy at that path. The solo path has no trunk-defined origin either, and needs none: `keys_visible=true` already fails precondition 2 by construction there (§7.4, §13 R11), so the narrowed rule adds nothing to it and takes nothing from it.

### 8.2 Shape

Absent, unreadable, or violating §4 in any particular: the finding is `result-missing` or `result-malformed`. **These are G1 findings, not states**: the run proceeds to a gate report and a review state like any other failing gate, and §8.7 says what may bypass them. **There is no partial ingestion** — a malformed file yields no outcomes at all, never "read what parsed". Reading a truncated file partially is how a cut-short `base` section would silently shrink the floor.

This step is §4 alone — framing, canonical form, record kinds, key sets, value grammars including `runner`'s lexical form, section order, sort order, `ids=` agreement, and the uniqueness of `(runner, id)` within each section. Whether the file's runner *tokens* are ones this repository declares is a policy question and is checked at §8.3 step 3, after the labels agree.

**Neither finding is ever raised for want of provider evidence** (§8.1). `result-missing` means no file was found at the path §8.1 fixes; `result-malformed` means a file was found and §4 or §8.3 step 3 rejected it. A file whose origin the run could not establish is neither: it is present and it is well-formed, so it is ingested, and the failure it produces is precondition 2's (§8.4), whose remedy is a human reading rather than a G1 finding. The two vocabularies do not overlap, and the distinction matters because `result-missing` in the quick lane is terminal (§8.7) while a precondition-2 failure never is.

### 8.3 Labelling, in this order

1. **`tree=` or `base=` ≠ the `(T, B)` this run fixed → `base-moved`.** The run ends and re-queues on the new tip; `C-M3` bounds re-verifications within the run (§5.4 step 6). §7.4 rule 3 names only `tree=`; `base=` is included here because two different bases can yield one tree — a tombstone's tree equals its parent's — and the collector read its pin and its policy at `base=`, so a different base is a different policy read (§13, R8).
2. **`tool=` ≠ trunk's `cli.version` + `cli.dist_hash` → G15 failure, never a retry** (§7.4 rule 3). The trusted stage constructs the expected token — `<cli.version>` `+sha256:` and `<cli.dist_hash>` **with its stored `sha256:` prefix removed** — from trunk's manifest and compares it to the header's `tool=` **as bytes over the whole token**. The prefix is written once: MF §3 stores `dist_hash` already prefixed (MF §8.3's manifest carries `"dist_hash":"sha256:6f49644f…744db"`), so repeating it would yield `1.4.0+sha256:sha256:6f49…`, which is outside §4.2's grammar for the field and is not §10's published `tool=`. No parse of the collector's token is required, and none is performed.
3. **A `runner` value the repository does not declare → `result-malformed`.** Every distinct `runner` value in the body must be a token the pinned release assigns to a language in trunk's `params.langs` (§6.2). One that is not means the file carries records from a suite this repository has not agreed to run, which a conforming collector cannot produce — by step 1 it read the same `base=`, and by step 2 it is the same build — so the file is malformed rather than merely surprising. **Absence is not checked**: a runner in the invocation set that contributed no records is indistinguishable from one whose suite is empty, and §14 OPEN-6 states the residual that leaves.

The order of steps 1 and 2 matters and is the opposite of intuition. An upgrade landing on trunk mid-run changes the pin *and* moves the base; checking `tool=` first would report a spurious, unretryable G15 on what is honestly contention, while checking the labels first yields `base-moved` and a retry that picks up the new pin. A genuinely unpinned collector on a stationary base still reaches step 2 and still fails G15, and `C-M3` bounds the loop either way. **Step 3 is last for the same reason** (§13, R30): a landing that removes a language from `params.langs` changes policy *and* moves the base, so a runner check before step 1 would turn honest contention into an unretryable `result-malformed`.

**There is no step 4, and provenance is not one.** §8.3 has exactly three steps and each is a comparison against a value read from trunk or computed by this run. Trunk-defined origin evidence is not among them: it decides no label, produces no retry and yields no finding, and it is evaluated once, at §8.4, as the third conjunct of precondition 2. An implementation that inserted it here would resurrect the withdrawn strict reading under another name (§8.1, §13 R31).

`C-M3` counts re-verifications **within one run**, in a counter the run holds in memory (§5.4 step 6). A `base-moved` exit ends this run and re-queues it; whether another run starts is the CI system's business. Nothing in this spec is stored across either.

### 8.4 Preconditions of §7.4 rule 5

Neither of these refuses ingestion. The design's answer to weak isolation is always that a human reads the landing, never that nothing happens.

- **Precondition 1** holds iff trunk's `params.isolation` is `container` — the one boundary v1 ships a mechanism for (PB §7.4 rule 5) — **and** the header's `profile=` equals it. `params.isolation` absent means `none`, so it fails; `uid` is not an alternative here, because no v1 collector writes that header value and `manifest.md` §6.2 check 12b keeps it out of trunk in the first place (§7.1). A disagreement — including a manifest claiming `container` against a header reporting `none` — fails the precondition and no more (§13, R9). There is no per-runner refinement: one profile covers the whole file (§3).
- **Precondition 2** holds iff **all three** of: `keys_visible=false`; §8.3 step 2 passed; **and this run established trunk-defined origin evidence for the ingested file** (§8.1). `keys_visible=true` fails it (§13, R10). A `tool=` mismatch fails it too, and independently fails G15 (§8.3 step 2). Absent or disproved origin evidence fails it, and does nothing else at all (§13, R31).

The third conjunct is the one the owner's decision of 2026-08-26 added, and it is a **narrowing**: nothing that failed precondition 2 before passes it now, and a run that has the evidence is in exactly the position it was in before. Under `--ci github` the conjunct holds on every conforming run and the precondition is unchanged. Under `--ci gitlab` with in-repository configuration and under `--ci generic` it never holds, so precondition 2 is unmet on **every** run in such a repository, forever — which is why `spine init` refuses to write `merge.auto = on` for either (`ci.md` §8.1, §9.3, §14 R14). That refusal is a refusal to *write*: a human may edit `C-M4: on` by hand, and this precondition is what makes the edit buy nothing.

Either failure makes `C-M4` evaluate `off` whatever the constitution says, and raises the `class=tripwire` `G11` wire naming the failed precondition, `reason=` mandatory (§5.2, §7.4 rule 5). **One wire, however many conjuncts failed**: precondition 2 is a single precondition with a three-part test, the wire is keyed `(G11, pathless)`, and a set carrying two `G11` entries is a wire set no conforming implementation reproduces (`gate-report.md` §5.8). Which conjunct failed lives in the review's `reason=`, which is prose a human writes and no artifact re-encodes. Under the shipped `C-A3: hostile`, precondition 0 has already failed and that wire is present on every run that tests anything (§11, Wire aggregation).

The header's `profile=` is the strength of G1's own evidence and is sealed into the landing as `profile=` (§6.3 G1, §11 `Spine-Seal`), so the ledger says for every landing forever how strong the evidence behind its green suite was.

**The seal's `profile=` when nothing was ingested.** A landing that ran gates but ingested no file — `result-missing` or `result-malformed`, bypassed under §8.7 — seals `profile=none`. `n/a` is reserved for landings that run no suite (§8.6); a seal must never claim a boundary no header established, and §11's seal grammar admits no fifth value.

**The seal's `profile=` when the ingested file's origin could not be established.** It is **the header's own value**, unaltered — `container`, `uid` or `none` as the header reports it — and the landing is fully representable: a header was ingested, so §11's seal grammar has a value to carry and `gate-report.md` §5.9's `evidence` object is present with every member read from that header. Three readings were available and two are refused. **`n/a` is refused**: a suite ran, and `n/a` is the tombstone's (§8.6). **`none` is refused**: `none` is a claim *about a boundary*, and downgrading a header that honestly reports `container` would put a false fact in the ledger to express a doubt that has its own field. What carries the doubt is precondition 2, recorded `"unmet"` in the report and signed over by the human the `G11` wire compels — so the ledger reads *this landing's collector claimed a container, and nothing established that the collector was ours*, in two members that cannot be confused. A reader wanting the strong reading takes `profile=` **and** `automerge.preconditions[2].status` together, which is the pair the design has always intended: a header alone proves nothing (§7.4 rule 5, precondition 1's own argument).

### 8.5 Evaluation

With the file ingested, G1 evaluates:

0. **`end.status` is `complete`.** Otherwise **G1 fails**: no pair counts as passed (§7.3), and no pair counts as *collected* either, so no clause below can be satisfied — including for runners that individually completed, since the file carries one status and it is the fold. Clauses 1–3 are still evaluated and reported, so the finding names which pairs the file failed to account for — but the G8 allocation of clause 2 is **not** made: a killed or crashed run is no evidence that an id stopped collecting, which is the question G8 asks and the one a partial run cannot answer.
1. Every frozen `Spine-Test` entry, parsed to `(R, F)` by §6.5 and evaluated by the roll-up there. A failure names the runner and the function id, in the `Spine-Test` line's own spelling, so a reviewer reading the wire and a reviewer reading the approval commit see the same bytes.
2. Every `base` record, by full-pair equality — and the finding is allocated between G8 and G1. Let `b` be a `base` record for which no `result` record has all of `r.runner == b.runner`, `r.id == b.id` and `r.out == "passed"`. Two shapes, which the file distinguishes:
   - **`b` went away** — no `result` record has `r.runner == b.runner` and `r.id == b.id`.
   - **`b` did not pass** — some `result` record has `r.runner == b.runner` and `r.id == b.id` and `r.out ≠ "passed"`.

   **The `xfail`/`skipped` carve-out is evaluated first, and it is a carve-out from both gates.** Where `b.out` is `"xfail"` or `"skipped"` **and** the shape is *did not pass*, `b` yields **no finding at all** — not G1's, not G8's — and therefore no wire, nothing for a review to cover, and `G1=pass` with `G8=pass` on `b`'s account. This is §6.3's exemption. **Both rows there carve out the same case; neither states it in the other's words**, so this document quotes each and relies on the case, not on the phrasing. G1's limb (ii) reads *"For an id in the `B` floor — **never for a frozen id** — where that id's own collected outcome on `B` was already `xfail` or `skipped` and it still collects on `T`"*; G8's reads *"an id whose own collected outcome on `B` was already `xfail` or `skipped` and which still collects on `T`"*. The two agree on every element that decides an allocation — `B`-floor ids only, `b.out` only, both of its two exempt values, the *did not pass* shape only — and `gate-report.md` §6.3's carve-out paragraph quotes G8's spelling, which is the shorter of the two. The datum is the `base` record's `out` member (§4.4), which exists for this and for nothing else.

   Three things about it are decided here rather than left to an implementer, because each is a place two implementations would otherwise write different wire sets.

   - **It is decided on `b.out` alone and never on the `T` outcome.** That is §6.3's own wording and it is also the only total reading. An id trunk itself reports as expected-to-fail, or as skipped, asserted nothing on trunk, so no outcome on `T` can retire evidence the floor never held: `xfail`, `failed`, `error`, `skipped`, `xpass` and `unknown` on `T` all leave it asserting exactly what it asserted before, which is nothing. A reading that additionally required `r.out == "xfail"` would re-arm the trap from the other side — repairing the underlying bug turns `xfail` into `xpass`, `xpass` is not a pass (§5), and the quick lane has no override (§8.7), so a repository would be blocked for fixing itself. The same reading over `skipped` re-arms the same trap the same way: un-skipping a landed test and finding that it fails would block the landing, when what the failure reports is trunk's own untested ground and not a regression this landing introduced.
   - **It does not reach the *went away* shape, and that is the boundary.** An id that stopped collecting is a harness change — the file was edited, deleted or renamed — and routing harness changes to a human is G8's whole job (§6.3 G8). Whether the id was `xfail` or `skipped` says nothing about whether the harness moved, so a vanished `xfail` or `skipped` id is allocated below exactly as any other vanished id is, and still takes a `class=protected` `G8:<path>` review.
   - **It does not reach clause 1.** A frozen `Spine-Test` entry is an approval's own promise about ids a human signed as evidence for an acceptance criterion, and §6.5 evaluates it at *function* granularity while `b.out` is a fact about a full id — a parametrized function with one `xfail` or one `skipped` case and three passing ones has no single `B` outcome to read. Confining the carve-out to clause 2 costs the deadlock argument nothing: a quick-lane and a toolkit-lifecycle landing have no frozen ids at all (§8.6), so clause 1 is vacuous in exactly the lanes where no override is reachable (§8.7).

   **What the carve-out can and cannot release.** It reaches only ids whose `b.out` is `xfail` or `skipped`, and an id that was passing on trunk has `b.out == "passed"`. So it can never mask a landing that broke a working test: the only ids it releases are ones from which no landing ever drew evidence. That bound is what makes it safe to decide on `B`'s outcome alone, and it is why the datum is read from a checkout of `B`, where no candidate process has run (§7.1 step 7, §9), rather than from `T`.

   Otherwise — that is, for the *went away* shape whatever `b.out` says, and for the *did not pass* shape where `b.out` is neither `"xfail"` nor `"skipped"` — both are a **G8** finding `G8:<b.path>` — §6.3 G8's *a landed id `T` no longer collects or does not pass* clause, and §4.3's *an id collected on `B` but absent from `T`'s collection is a G8 failure* — and G8 does not fail on `b` where a verifying `class=protected` review's `wires=` contains `G8:<b.path>`. **G1 fails on `b` as well**, save — for the went-away shape only — where that same review names `G8:<b.path>`: §11 writes G1's exemption over *the path whose ids went away*, and it does not reach an id that collected and failed. An empty `b.path` names no path, can satisfy no exemption, and is a G1 finding (§13, R19).

   **A wire names a path, not a pair.** `G8:<path>` carries no runner qualifier and gains none here: a path is a path, and §11 closes the wire's grammar. So where two runners collect ids from one file — a polyglot test file, or a repository migrating between two runners over the same sources — one `class=protected` `G8:<path>` review discharges the finding for *both* runners' ids at that path. That is the correct reading and not a gap: the reviewed act is the change to the file, which is one act however many runners read it.
3. Every AC of a `tests-approved`+ intent has at least one `verified_by` edge whose target `test` node parses to a pair `(R, F)` with `P(R, F) ≠ ∅` under the roll-up of §6.5 — that is, some `result` record has `r.runner == R` and `r.fn == F`, which subsumes `r.id == F` because `fn == id` for an unparametrized id. **Outcome is irrelevant; collection is the test** (§6.3 G1: *≥1 `verified_by` edge with a collected id*). The match is on `(runner, fn)` because a `test` node id is `test:<runner>:<id>` (§6.2) and `Spine-Test`'s ids are *function* ids qualified by their runner (§4.3, §11) — for example `test:vitest:tests/billing/invoice.test.ts > invoice totals > AC1 includes tax` — and a parametrized function id never appears as a `result` record's `id`, only as its `fn`. Matching on `id` would fail every parametrized AC test, this document's own §10 included; matching on a bare `fn` across runners would let one runner's collection satisfy an AC verified in another.

A finding about an id that collected on `T` and did not pass cites that pair's `result` record `path`; a finding about an id that went away cites its `base` record `path` — which is the path a `class=protected` `G8:<path>` review must name for either exemption of clause 2 to apply. Where the two records for one pair disagree on `path`, that is not an error and neither record is rejected.

**The wire token of a G1 finding.** A finding needs a token or no review can name it, and `gate-report.md` §6.3 fixes the `class` and adopts the token from here rather than inventing one across the boundary. Two things rest on getting one answer: two implementations that spell a G1 finding differently write different `wires` arrays, hence a different `report=` and a different `envelope=` over identical objects (`gate-report.md` §6.1); and on a `Spine-Event: reseal` landing, where break-glass is unreachable and the only discharge is the reseal's own `class=protected` review **naming the finding's token** (§8.7, §8.6, `gate-report.md` §5.6.1's reseal row), a finding with no token is a finding no review can admit — so an orphan range containing one landed test that failed would be a trunk nobody can land on, the deadlock that row exists to prevent.

**A per-id finding takes `G1:` + `tok(path)`**, where `tok` is `gate-report.md` §6.2's token encoding — `esc` with `,` (`0x2C`), `U+0020` and `"` (`0x22`) moved into the `\xHH` row, in one pass over the bytes — mirroring `G8:<path>` and every other per-path gate. **Which record supplies the path is the paragraph above's rule, read by record presence**: the pair's `result` record `path` where the file carries one, its `base` record `path` where it does not. For a file whose `end.status` is `complete` that is exactly the *did not pass* / *went away* split; for a file whose status is anything else it also settles the pair whose `result` record says `passed` and which clause 0 fails anyway, and that pair's path is its `result` record's. Per clause:

- **Clause 1** raises one entry per member of `P(R, F)` whose `out ≠ "passed"`, over that member's `result` record `path`.
- **Clause 2**, *did not pass*, raises one over the pair's `result` record `path`; *went away* raises one over the `base` record's `path` — the same bytes its `G8:<b.path>` entry names, so one `class=protected` review covers both gates by naming both tokens.
- **Clause 0** leaves the allocation of clause 2 to G1 alone, so a partial run's clause-2 entries are G1's and no `G8:<path>` entry accompanies them; the paths are unchanged.

**The bare `G1` is what is left, and it is a closed list of five.** Each names no path, so under PB §11's *"gates without a path use the bare id"* it takes the bare form:

1. `result-missing` (§8.2, §8.7).
2. `result-malformed` (§8.2, §8.7).
3. **Clause 0's own finding** — `end.status ≠ complete` is a fact about the file and about no pair. It is raised *in addition to* whatever clauses 1–3 then raise, not instead of them.
4. **Clause 3's uncovered AC** — the finding names an acceptance criterion, and an AC with no collected `verified_by` edge has no `result` record to take a path from.
5. **Clause 1 where `P(R, F)` is empty** — the frozen entry collected nothing, so there is no `result` record, and a frozen `Spine-Test` entry carries no path of its own (§4.3, §6.5: a `Spine-Test` payload is `<runner>` `U+0020` `<function id>`; `Spine-Frozen` is where paths live, and the join from an id to one is not this document's, §12). Where the same pair is also in the `B` floor, clause 2 raises its own `G1:<b.path>` entry independently; the two coexist, `gate-report.md` §6.1 keying the pathless entry distinctly and ordering it first, its token being a proper prefix of theirs.

**An empty `path` is no path, and takes the bare `G1`.** §4.4 emits the empty string where no tree entry matches the runner's reported path. `G1:` with nothing after the colon is never written: it is not the bare id and it names nothing, so it could be neither cited by a reviewer nor distinguished from a typo. This is the same fail-closed direction §4.4 and the paragraph above already take for G8 — *"an empty `b.path` names no path, can satisfy no exemption, and is a G1 finding"* (§13, R19) — and it keeps every token this document emits inside `gate-report.md` §6.2's grammar.

**One entry per path, never per pair.** `gate-report.md` §6.1 keys the `wires` array on `(gate, path)` with the pathless case a distinct key, so two failing ids collected from one file, and a parametrized function's several failing ids, collapse to a single `G1:<path>` entry — exactly as two offending pragmas in one blob collapse to one `G5:<path>` there. The wire set is per path; *which pairs* failed is the review packet's (§12), and this file's `result_sha256` pins the bytes that say so.

### 8.6 Landings that ingest nothing

A **tombstone** changes no tree, runs no suite and is exempt from §7.4 rule 5 entirely (§11, *Landings that run no suite*). No result file is expected, its absence is never a G1 failure, and `Spine-Gates` lists only G9, G13, G14 and G15. **Quick-lane and toolkit-lifecycle landings do run gates** (§6.7) and do ingest a file; having no frozen ids, their G1 is the `B` floor alone — across every runner — and the AC clause is vacuous. These are the lanes §8.5 clause 2's `xfail`/`skipped` carve-out exists for: clause 2 is the whole of their G1, and no override of any class is reachable to them (§8.7), so an id trunk itself reports `xfail` or `skipped` would otherwise be a G1 **and** a G8 finding on every one of their landings, on this one and on every later one, because trunk has not changed.

**A reseal runs the suite and ingests a file** (§13, R22). **It is exempt from nothing**: PB §7.4 rule 5, as of v0.19, says so in terms — a reseal *"does run the suite, does ingest a result file, and seals the real `profile=` that file reports — never `n/a` … preconditions 1 and 2 are evaluated for it like any other landing that tests something"* — and `gate-report.md` §5.8 records the same rule as "**A reseal is exempt from nothing.**" So a reseal computes all five preconditions like any other landing that tests something, and §11's *Landings that run no suite* names only the tombstone. Its labels are fixed: `base=` is the seal's `base=` — the last valid landing below the range, from which every policy read for a reseal is taken (§5.5), **`params.langs` and `params.timeout` included** — and `tree=` is `tree(O)`, because the reseal branch `refs/heads/quick/reseal-<O>` is branched from the orphan tip `O`, so `Hc = O`, `base=` is an ancestor of `O`, and `merge-tree(base, O) = tree(O)`. G1 and G8 findings inside the range are sealed `=override` and counted as freeze overrides (§5.5), admitted by the reseal's own `class=protected` review naming each token (§8.7). **A reseal whose file is absent or malformed is not exempt and is not refused**: `result-missing` or `result-malformed` is a G1 finding, that same review admits it, and the landing seals `profile=none` (§8.4) instead of the ingested header's value.

### 8.7 Overridability

G1 and G8 are both in the break-glass bypass list; G15 is not (§11, Gates). So `result-missing`, `result-malformed` and every G1 and G8 finding above can be bypassed by a signed `class=break-glass` review, recorded `=override` in `Spine-Gates` and counted forever as a freeze override (§7.6). **On a `Spine-Event: reseal` landing there is a second route and break-glass is not available at all**: the reseal's own `class=protected` review naming the finding's token admits it, with the same `=override` entry and the same freeze-override count (PB §5.5, `gate-report.md` §5.6.1's reseal row; below). A `tool=` mismatch can not be, in any mode, by anyone. Neither G1 nor G15 ever runs in warn-before-block mode.

**Break-glass does not reach every lane.** It is available only from `tests-approved` onward — never before an approval exists (§7.6) — and the transition table admits it from `tests-approved`, `landing-review`, `protected-review` and `base-moved†` only (§6). A quick-lane candidate and a toolkit-lifecycle landing have no approval and never enter those states, while §8.6 has them ingesting a file like anything else. So **in the quick lane a `result-missing`, `result-malformed` or G1 finding is terminal**: the exits are a conforming run, or promotion to the gated lane (`spine new --from <branch>`). **A reseal is the one quick-lane shape this does not reach, and the exception is normative.** PB §5.5 gives a `Spine-Event: reseal` landing a `class=protected` review of its own, folds every wire into its `wires=`, and says the landing *"is never escalated and never refused by a wire"* and that *"a G1 or G8 finding inside the range is sealed `=override` and counted as a freeze override"* — so on that shape every G1 and G8 finding, `result-missing` and `result-malformed` among them, is admitted by that review naming its token and the gate reads `override` (`gate-report.md` §5.6.1's reseal row; §8.6 above). It has to be: a reseal can take neither exit — its tree must equal `O`'s, so there is no candidate to fix, and a reseal is not promotable by `spine new --from` — while G9 refuses every landing above an orphan until the reseal lands, so a terminal finding there is a trunk nobody can land on. Break-glass is still unavailable to it (PB §5.5); the protected review is the route. This is what §5's `xfail`/`skipped` carve-out is bought against — an id trunk itself reports as expected-to-fail, or as skipped, would otherwise be a G1 and a G8 finding on every landing here, with no override of any class reachable — and it is what makes a chronically slow runner a governance problem rather than a nuisance — a quick-lane landing that trips `params.timeout` has no override at all, and the remedy is a reviewed change to trunk's `params.timeout` or to the suite.

**An override for a missing file is re-signed on every base move.** `result-missing` and `result-malformed` are findings about G1 as a whole and name no path, so the review that bypasses them carries a **bare** `G1` in `wires=` (§11) — and a review whose wire set carries a pathless wire never survives a base move (§5.4 table, §12's v0.16 note 1): the path test that bounds what a base move may touch is vacuous against a wire that names nothing. **A per-id finding is the other way round, and §8.5 is why**: its token names a path, so a review covering only per-id G1 findings survives a base move that touches neither the floor nor those paths, exactly as the `G8:<path>` review over the same act always has. The five bare findings §8.5 lists are the pathless ones, and only they carry this cost.

## 9. What a candidate can and cannot influence

§7.4's whole argument rests on this line, so it is drawn explicitly. "Candidate" is the branch's code and everything it can reach at build or test time.

**The *cannot* table is conditioned on trunk-defined origin evidence (§8.1), and says so in each row it depends on.** Every entry in it derives from *the collector wrote this file*, and that premise is what the evidence establishes. Where the run has no such evidence the untrusted job's definition may be the candidate's own, so the job that was supposed to invoke the collector need not have invoked it at all — and then the file is a candidate artifact end to end, with no row of the first table holding. That case has one answer and it is precondition 2 (§8.4), never a refusal; it is why the narrowed rule is fail-closed rather than merely permissive, and it is stated here rather than left implicit because a reader who takes the first table unconditionally will believe a GitLab-in-repository landing proves things it does not.

| Cannot influence | Because |
|---|---|
| That the file exists, and who authored it | The collector writes it, holding the pipe and the directory; under `container` or `uid` no runner has a write path to it (§7.4 rule 3). **Conditioned on origin evidence** (§8.1): without it, whether the collector ran at all is the untrusted definition's business, and the definition may be the candidate's |
| **Under `container` or `uid`, and with origin evidence:** any of the six header fields | Every one is produced by the collector from its own observation or from trunk. Under `none` the collector owns nothing — the last row of the second table says so. Without origin evidence every field is a string copied out of trunk's manifest by whoever wrote the file, `keys_visible=false` and `profile=container` included — the second-to-last row of the second table |
| **Which runners run** | The invocation set is a function of trunk's `params.langs` and the pinned release (§6.2). A candidate cannot add a runner, drop one, or reorder them into relevance — the sort of §4.5 removes order from the bytes |
| **The `runner` token on every record** | It is a constant embedded in the pinned release's adapter, never read from the runner's stream, the tree's configuration or the environment (§4.4). It is the one part of the identity `(runner, id)` that candidate code never touches |
| **The deadline** | `params.timeout` is read from trunk (§7.1), is on the protected floor with the rest of `.spine/**` (§7.3), and no candidate-supplied value is consulted |
| **Egress, and the restore script** | Under `container`, every runner invocation is spawned loopback-only and **P4 tested that** at step 6, before any repository process had run (§7.1), so a candidate cannot give its own tests a route off the host. The one phase that keeps the job's network runs `.spine/restore.sh` read from `origin/<trunk>` and never from a checkout, on the protected floor with the rest of `.spine/**` (§7.3) — so the egress window is trunk's, opened by a landed protected review or not at all. Under `none` no boundary is attempted and this row says nothing |
| Which tree the results are about | The trusted stage ingests only a file labelled with the `T` it computed itself; anything else is `base-moved`. "A pass against any other tree is not a pass" (§6.3 G1) |
| Which release wrote it | `tool=` is the collector's own embedded constants, checked against the base's pin — G15, never a retry |
| **Membership of the `B` pair set** | Every runner's collection happens on a checkout of `B` before any process has run against `T`'s content, and with no selection argument (§7.1 step 7). A landed test cannot be made uncollectable by any runner; it can only be made to fail or vanish on `T`, and both are G8 and G1 failures (§8.5) |
| **Every `base` record's `out`** — the datum the `xfail`/`skipped` carve-out reads | It is trunk's own code reporting on trunk's own tree: the `B` outcome run is a `B` invocation, so it precedes every `T` execution by §7.4 rule 3 and no candidate process exists when it runs (§7.1 step 7). A candidate therefore cannot put an id **into** the exempt set, which is the only direction that would buy it anything — the carve-out releases ids trunk itself reports as expected-to-fail or as skipped, and making an id `xfail` or `skipped` on trunk requires landing that change on trunk, which is a gated act in its own right. Taking an id **out** of the set is available to it and worth nothing: it withholds an exemption from itself. **Conditioned on origin evidence** (§8.1) exactly as the rows above are: without it, whether the collector ran the `B` outcome run at all is the untrusted definition's business |
| The framing, ordering, canonical form, or the `end` record | All serialized by the collector after reaping every process group |
| Whether the file is ingested, and what G1 concludes from it | Trusted stage, pinned release, policy from trunk |
| Whether a human reads the landing | Under `C-A3: hostile` precondition 0 fails on every run and the `G11` wire is universal (§10 budget row 1) |

| Can influence | Bound |
|---|---|
| Every `out` value, and every id, `fn` and `path` string in the `result` section | Frozen tests import the code under test, so the candidate's code and its runner share a process; a runner that monkeypatches the reporter or the assertion library lies on the stream the collector faithfully records. **This is the residual §7.4 names and does not close.** G1's `passed` is exactly as strong as the isolation between a candidate's code and its own runner, and nothing establishes that property. It is now *per runner*: a candidate that can lie in one runner lies about that runner's ids only, and the pair keying is what confines it |
| Which of several reported outcomes for one pair is transcribed, where trunk's own frozen configuration reruns | §7.2's last-terminal-outcome-wins is **fail-open**: a `failed` followed by a `passed` is a pass. The candidate cannot introduce the rerun — the configuration is frozen under `C-T2` and the repo chose it — but it can trigger it (§13, R6) |
| Whether a runner crashes, hangs, or emits nothing | Fail-closed: `status ≠ complete` credits nothing, so G1 fails. **One runner is enough**: the fold means hanging the cheapest runner in the set fails the landing as surely as hanging them all — a denial of service against one's own landing, never a pass |
| Whether the deadline expires, by making a suite slow | Fail-closed, and bounded: the expiry is `runner-timeout`, which credits nothing. The only thing a candidate buys by hanging is a failed landing and, in the quick lane, an unoverridable one — a reseal excepted (§8.7) |
| Which ids are collected on `T`, in any runner | Adding tests is permitted inside the harness rules; removing, renaming or skipping a frozen or landed id is a G8 or G1 failure by identity (§4.3, *Skipping is modifying*). Changing what a landed test parametrizes over removes ids from `T` that `B` collected — G1 fails and names them. The `xfail`/`skipped` carve-out of §8.5 clause 2 is not a way in: it releases only ids whose *`B`* outcome was `xfail` or `skipped`, which is trunk's report and not the candidate's, and it does not reach the went-away shape at all. Moving a test from one runner to another changes its pair, so the old pair goes away and the new one is not the old one: a G8 and G1 finding, and the reviewed path is the `G8:<path>` one |
| **The whole file, where the run has no trunk-defined origin evidence** | The untrusted job's definition is the candidate's, so the job that should invoke the collector may invoke nothing and write the file itself; every header field is then a forgery that §8.3 passes by construction, because §8.3 compares the header against trunk and a forger reads trunk too. Bounded by precondition 2, which is `unmet` on every run in such a repository (§8.4) — so no landing there auto-merges, each takes a human reading, and `spine init` refuses `merge.auto = on` up front (`ci.md` §8.1, §9.3). This is the case the withdrawn strict reading tried to answer by refusing every file, which answered it by deleting two providers (§13, R31) |
| The whole file, under `profile=none` | The collector owns nothing; any process in the job can write it. Precondition 1 fails, so no run auto-merges on it, and the design says so rather than pretending (§7.4 rule 3) |

**G6 is not a repair.** It runs in the same untrusted stage and reports through the same collector, so a runner that lies about the suite lies about the mutants (§6.3 G6). It is a strength signal, never an integrity control.

**How the trusted stage reads it.** The artifact holds one file at that path. `tree=` equals the stem and the `T` this run computed; `base=` equals `B`. `tool=` equals trunk's `1.4.0` + `sha256:6f49…`, compared as one token — the release 1.4.0 `dist_hash` `manifest.md` §8.2 computes over its published artifact list, which is the one value the corpus uses for this release. Both `runner` values are tokens the pinned release assigns to `python` and `ts`, which are trunk's `params.langs` — §8.3 step 3 passes. `ids=7` equals the seven `base` records, four pytest and three vitest. `status` is `complete` — which required **both** runners to complete — so outcomes count and clauses 1–3 are credited.

- Both sections are sorted on `runner` bytes first: every `pytest` record precedes every `vitest` one, because `p` < `v`. Within each runner the sort is on `id` bytes, which puts `…::test_AC1_…[reduced-rate]` before `[standard-rate]` before `[zero-rate]`, and `…half-even` before `…half-up`.
- Frozen `("pytest", …::test_AC1_totals_include_tax)` → `P(R, F)` is the three parametrized records, all `passed` → pass. Frozen `("vitest", …> AC2 zero-rated lines)` → one record, `passed` → pass. Neither roll-up looks at the other runner's records, and neither would find them if it did.
- The seven `base` pairs each have a `result` record with the same `runner` **and** the same `id` and `out: passed` → the floor holds, and neither G8 nor G1 has a finding to allocate. Note that the branch's own two tests are absent from section 2: they are not trunk's, and they enter the floor only when this intent lands.
- Every `base` record reads `out: passed` because trunk is green. That member is read by exactly one rule and it does not fire here: no `b.out` is `xfail` or `skipped`, so §8.5 clause 2's carve-out is inert and the allocation runs unchanged. `out` on a `base` record is never consulted as evidence that anything passed — the seven pairs above are credited by their **`result`** records, and would be credited identically if trunk's own run had reported every one of them `skipped`.
- AC-1's and AC-2's `verified_by` edges name *function* ids qualified by runner — `test:pytest:tests/billing/test_invoice.py::test_AC1_totals_include_tax` and `test:vitest:tests/billing/invoice.test.ts > invoice totals > AC2 zero-rated lines`. The first appears nowhere as a record's `id`; it resolves through `(runner, fn)` on the three parametrized pytest records, so `P(R, F) ≠ ∅`. The second resolves through the one vitest record whose `fn` equals its `id`. Both satisfy §8.5 clause 3 → the coverage clause holds. G1 passes.
- `profile=container` equals `params.isolation` → precondition 1 holds. `keys_visible=false`, a matching `tool=`, **and trunk-defined origin evidence** — the trusted job ran on a `workflow_run` of `.github/workflows/spine-collect.yml` in this repository (`ci.md` §14 R11) — → all three conjuncts hold, so precondition 2 holds (§8.4). Precondition 0 fails anyway, because `C-A3` is `hostile`: `C-M4` evaluates `off`, G11 raises its `class=tripwire` wire naming precondition 0, and the landing takes one human reading — which the author may sign (§7.4 rule 5). `Spine-Gates` records `G11=pass`: the precondition wire is G11's own and is not a finding about G11, and PB §11's `Spine-Gates` row says exactly that — "a gate that ran and passed its own check reads `=pass` even when it raised a wire — the rule-5 `G11` precondition wire is not a finding about G11". `G1` reads `pass` here for the ordinary reason: it had no finding.
- The landing seals `profile=container threat=hostile`, so the ledger records forever how strong the evidence was.

**One `xfail` on trunk, which is the case `out` exists for.** Suppose trunk's `tests/billing/test_discounts.py::test_percentage_discount` is marked `@pytest.mark.xfail` and has been for months. Its `base` record reads `out: "xfail"` and its `result` record reads `out: "xfail"` as well. Under §8.5 clause 2 it is the *did not pass* shape with `b.out == "xfail"`, so it produces **no finding in either gate**: `Spine-Gates` still records `G1=pass` and `G8=pass`, `wires` is unchanged, and this landing needs no review it did not already need. Every other byte of the file above is the same, `ids=7` is the same, and the two `out` members that moved are the only difference. Without the carve-out the same file would fail G1 *and* G8 on that one pair, on this landing and on every later one, and — since this repository's quick-lane landings never reach `tests-approved` — with no override at all (§8.7).

| What trunk reported on `B` | What `T` reported | Finding |
|---|---|---|
| `xfail` | `xfail`, `failed`, `error`, `skipped`, `xpass` or `unknown` | **none**, in either gate — the carve-out, decided on `b.out` alone |
| `xfail` | nothing at all (the id went away) | G8 `G8:tests/billing/test_discounts.py`, and G1 unless a `class=protected` review names that path — the carve-out does not reach this shape |
| `skipped` | `skipped`, `failed`, `error`, `xfail`, `xpass` or `unknown` | **none**, in either gate — the same carve-out, over its second value, decided on `b.out` alone |
| `passed` | `xfail` | G8 and G1 both, as before: an id that *was* passing on trunk and is now expected-to-fail is a regression this landing introduced, which is the whole distinction |

**Had the two runners collided on an id.** Suppose the repository were migrating from jest to vitest and both collected `tests/core/util.test.ts > rounding > half-even`. That is two `base` records and two `result` records, `ids=` counts two, and neither section is malformed — the pair is the identity, and a duplicate is a repeated *pair*. Each runner's record credits only its own runner's frozen ids and its own floor entry, and a `G8:tests/core/util.test.ts` review would discharge a finding about either.

That is the cost of one `end` record, and it is deliberate: the file's whole credit rule is *`complete` or nothing*, and a run in which any declared suite did not finish is not a run whose green half should count. ## 11. Conformance checklist

An implementation conforms when, for every input:

1. Header field set, order, grammar and closed value sets are exactly §4.2 — still six fields, unchanged by multi-runner — and a repeated key rejects the file.
2. Body lines are canonical JSON per §4.3, on write **and** on read.
3. Record kinds, keys and value sets are exactly §4.4, `runner` included and matching its grammar, with unknown anything rejected — and `out` is present on **both** the `base` and the `result` kind, admitting `absent` on the former and rejecting it on the latter.
4. Ordering is exactly §4.5: sorted on `runner` bytes, then `id` bytes, in both sections.
5. Identity is the pair: `(runner, id)` is unique within each section, one `id` under two runners is not a duplicate, and no rule compares a bare id or a bare `fn` across runners.
6. `passed` is the only pass, and only when `status` is `complete`.
7. Frozen `Spine-Test` entries parse to `(runner, fn)` at the first space and roll up within their runner; `B` pairs match by full `(runner, id)`; an AC's `verified_by` edge resolves through `(runner, fn)`.
8. A vanished or failing `base` pair is allocated between G8 and G1 exactly as §8.5 clause 2 says, and `status ≠ complete` fails G1 before any clause is credited.
8a. The `xfail`/`skipped` carve-out is applied first and to clause 2 only: a `base` record whose `out` is `xfail` or `skipped` and whose pair still collects on `T` yields no finding in **either** gate, whatever `T` reported; the same record for a pair that went away yields the ordinary allocation; and no frozen `Spine-Test` entry is exempted by it (§8.5).
8b. A G1 finding's wire token is exactly §8.5's: `G1:` + `tok(path)` for a per-id finding — the pair's `result` record `path` where the file carries one, its `base` record `path` where it does not — and the **bare `G1`** for the five findings that name no path (`result-missing`, `result-malformed`, an `end.status` fold that is not `complete`, an AC with no collected `verified_by` edge, and a frozen entry whose `P(R, F)` is empty), and for any per-id finding whose `path` is the empty string. One entry per path, collapsed by `gate-report.md` §6.1's `(gate, path)` key. An implementation that spells any of these otherwise writes a different `wires` array, a different `report=` and a different `envelope=` over identical objects.
9. The invocation set is every adapter trunk's `params.langs` implies, invoked in full with no selection argument, and every one of a runner's `B` invocations — its enumeration and, where the adapter has a separate one, its outcome run — precedes every `T` execution.
10. A deadline is enforced on every runner invocation, `B` enumeration and `B` outcome run included, **and on each of the two restore phases**, from `params.timeout` read from trunk, defaulting to 1800 seconds; enforcing none is non-conformance. Expiry during a `B` enumeration is `base-collect-failed`; expiry during a `B` outcome run is not a status at all and leaves `out: "absent"` behind (§7.1, §7.3).
11. `end.status` is the fold of §7.3 over the table's fixed order, `complete` only when every runner completed, and a failed `B` collection in any runner suppresses the whole body with `ids=0`.
12. Ingestion follows §8's order, and `base-moved`, G15 and the undeclared-runner check land where §8.3 puts them.
13. The file contains no timestamp, no duration, and nothing derived from wall time.
14. Two runs over the same `(B, T)` with the same collector build, the same invocation set and identically-behaving runners produce byte-identical files whenever `end.status` is `complete`.
15. **A well-formed file whose trunk-defined origin the run could not establish is ingested**, evaluated in full, and fails auto-merge precondition 2 and nothing else (§8.1, §8.4). An implementation that refuses such a file, reports it as `result-missing` or `result-malformed`, downgrades the sealed `profile=` on account of it, or emits a second `G11` wire for it, is non-conformant.
16. **`profile=` is licensed by a test, not by a configuration** (§7.1). `container` is written only where `params.isolation` requests it *and* P1, P2, P3 and P4 all passed against a probe boundary built from the **runner disposition** every runner invocation then uses; `uid` is written by no v1 collector, and a manifest requesting it is refused at step 1 with no file written; `none` is written in every other case that reaches step 7, including every failure of M1 or of P1-P4, and on every run outside `--ci`, where no boundary is attempted and nothing is refused (§7.4). An implementation that writes `container` without having run the four tests, that answers a `uid` request with a file rather than a refusal, that substitutes one mechanism for another, or that runs any runner inside a boundary whose test failed, is non-conformant.
16a. **Egress is the boundary's, and dependency restore is a phase and not a runner** (§7.1). Every runner invocation is spawned under the **runner disposition** — a network namespace holding only loopback — and the only phase that keeps the job's own network is the restore phase, whose bytes are read from `origin/<trunk>:.spine/restore.sh` and never from a checkout, which runs once per checkout before the first invocation against it, which is bounded by `params.timeout`, and which contributes no record, no id, no `status` and no read of its exit code. Absent on trunk, the phase is empty and every runner still runs loopback-only. An implementation that spawns a runner with egress, that takes the restore script from a checkout, that lets the restore phase contribute to the file, or that treats a missing script as a prerequisite failure, is non-conformant.

## 12. Out of scope

Deliberately absent, each for a stated reason:

- **Timestamps, durations, elapsed times, ordinals derived from wall time.** One clock and it is the chain (§7.5). They would also destroy §11's determinism claim. `params.timeout`'s value is policy and is not written here (§4.2).
- **Runner exit codes and signals.** Platform-divergent; no gate reads them; `status` carries every distinction the mechanism makes.
- **Per-runner status records, and any per-runner section of the file.** One `end`, one fold (§7.3, §13 R28).
- **Per-language and per-runner id grammars, `runner` tokens, `id → fn`, `id → path`, and the outcome mappings for the four v1 languages.** `import-resolver.md`, for all four in one place, so that two implementations cannot disagree on an edge case and reject each other's approvals (§6.4). This document fixes only the obligations and the checks that survive them.
- **How trunk-defined origin evidence is obtained, per provider.** `ci.md` — §10.3 scores the shipped arrangements and §14 R11 fixes GitHub's three-clause test. This document fixes only what the evidence *is* (§8.1), what it costs when absent (§8.4), and that its absence is never a refusal. A provider test written here would be a second, unsealed implementation of that document's job, and would go stale the first time a provider changed an event name.
- **The static import resolvers themselves.** `import-resolver.md`. This file never touches an import.
- **The source-symbol → runner-id join** — how a `@verifies` pragma or an `AC<n>` name in a blob becomes a runner-native id. Assumed by G1's coverage clause and by `Spine-Test`, defined by neither this spec nor `gate-report.md`, and **written in `import-resolver.md` §12** — §12.1 the pragma grammar, §12.2 the file-granular join over the `path` member this document's `base` records carry (§4.4), §12.3 the per-runner naming sugar. It sat with the per-runner specs, and that is where it landed; it is no longer a tracked gap.
- **How `freeze=` is computed over runner-qualified `Spine-Test` lines.** The sort that digest is taken over now orders on the runner token first, because it orders on the line's bytes. That is `envelope-vectors.md`'s to publish a vector for.
- **Failure messages, tracebacks, assertion diffs, captured stdout/stderr, and which runner failed.** The file is a gate input, not a report. Prose authored by a candidate inside an artifact the trusted stage parses is an injection surface (§7.1, *Injection defense*), and the human's evidence is the CI log and the `spine review` packet (§6.5).
- **Coverage data.** `exercises` edges are optional and v1.1, derived from CI coverage reports (§6.2). **There is no second channel in v1**: §11 makes this file the untrusted job's only artifact and §8.1 enforces it. v1.1 must either add a record kind here or raise §11's only-artifact rule — the owner's decision, not this spec's.
- **G6 mutation results.** §6.3 says G6 reports through the same collector; how is OPEN-5. It does not overload these record kinds.
- **Retry and flakiness metadata.** §7.2 reduces to one record per pair and says which one wins.
- **A signature, a MAC, or any envelope over the file.** Authority is the pin and the trigger (§2).
- **Publication of this file, or of anything derived from it beyond the gate report's `result_sha256`.** §7.4 rule 4 makes publishing the *gate report* to `refs/notes/spine` mandatory on every landing; this file is not that report, is never pushed to a note, and would be worthless there — it is keyed by a `T` that no longer exists and is credit for exactly one run. A note is never a source (§7.4 rule 4), so nothing this file says could gain authority by being published anyway.
- **Non-UTF-8 test ids** (§7.2).
- **The particular system call, helper or runtime that creates M1's namespaces.** `unshare(2)` used directly, a rootless OCI runtime, and a sandbox helper are all conforming if the probe of §7.1 passes P1-P4 under them, and none is named here: naming one would make a build's choice of helper part of the file's meaning, and P1-P3 already decide the only question the header records. What §7.1 does fix is the configuration M1 requires and the tests that license `profile=`. **This freedom is over creation and not over measurement**, and the two were one clause until §13 R36 separated them: P4(a)'s enumeration is normatively over **netlink** and never `sysfs` (§7.1), because a `sysfs` inherited across `unshare(2)` answers for the wrong namespace and a test that can be aimed elsewhere is a configuration claim, which §7.4 rule 3 refuses in the sentence that says *"a header alone proves nothing"*. No other test's source is fixed, because no other test has a source that can be aimed.
- **Container images, registries and image policy.** M1 pulls none and names none (§7.1), so there is no image to specify, no digest to pin and no manifest key to add. `ci.md` §17 defers image choice to this document; the answer is that the question does not arise.
- **Enforcement of `SPINE_ALLOWED_HOSTS` itself — the *which hosts* half, not the *when* half.** M1 now enforces *when*: every runner invocation is loopback-only and P4 tests it (§7.1). Narrowing the one phase that keeps the job's network — the restore phase — to the declared host list is still a network policy, a proxy sidecar or an egress firewall the host supplies, because a collector that filtered by hostname would be a second, unsealed copy of a control `.spine/ci.sh` already declares (`ci.md` §5.6). No gate, no precondition and no header field reads egress; what reads it is P4, and its whole output is `profile=`.
- **What a restore script contains, per language.** `.spine/restore.sh` is the repository's, not spine's: no v1 template writes one, no `files[]` record names one, and this document fixes only where its bytes come from, when it runs, what it runs under and that it contributes nothing to the file (§7.1). Fixing a restore *command* per language would be a fifth column on `import-resolver.md` §11.1's adapter table that three of the four ecosystems have no single answer for.
- **Retention, artifact naming, upload and download mechanics.** `ci.md`.
- **Anything that would make the file persist between runs.** There is no index, no manifest of past result files, no cross-run comparison, and no refusal that depends on a file already being there (§3). Nothing in this design may remember that a previous attempt happened (§5.4 step 6). This is also why §8.3 step 3 checks the runner tokens present and not the ones absent: comparing this run's runner set with a previous run's would be exactly that memory.

## 13. Resolved ambiguities

| # | What the playbook says | Resolution | Why |
|---|---|---|---|
| R1 | §11 fixes the header line and says "then the id set collected on `B`, then one record per runner-native id" — no framing, no record shape. | JSONL: header line, then `base` records, then `result` records, then one terminal `end` record; canonical JSON, `t` discriminator, byte-sorted sections. | `.jsonl` is fixed by the path §11 gives. A terminator is required because truncation of the `base` section shrinks the floor and is not otherwise detectable; sorting is required because report order is the file's only remaining clock. |
| R2 | `ids=<n>` is undefined between "the `B` id set" and "the result records". | `ids=` counts the `base` records, which under several runners is the cardinality of the set of `(runner, id)` **pairs**, not of bare id strings. | §7.4 rule 3 lists the `B` id set as part of what the header carries; `ids=` sizes the thing it introduces, and with `end` present the result count is already unambiguous. It cross-checks the collector against itself: file truncation is already caught by the missing `end` (§4.5), but a collector that emitted fewer `base` records than it counted is not. Counting pairs is forced by §4.3's *the pair is the identity*: counting bare ids would under-report a repository whose two runners collect one id string, and would make `ids=` disagree with the record count. |
| R3 | No field carries a function id or a path. | `result` records carry `fn`; both kinds carry `path`. | The §4.3 roll-up, §6.3 G1's AC-coverage clause and the `G8:<path>` exemption are not computable without them. The alternative — the trusted stage parsing runner-native ids — puts runner grammar into the stage that is meant to be runner-agnostic and executes no repository code. |
| R4 | G1 names "not skipped, xfail, deselected, or absent". `xpass` is not named. | `xpass` is not a pass. | An id whose declared polarity is "expected to fail" is not evidence an AC holds, and a strict expected-failure that passes is already reported as a failure by the runners that have the concept. |

| R6 | Nothing says what a repeated id means, and v0.19 makes a repository able to run several runners. | Collector: last terminal outcome wins, one record per **`(runner, id)` pair**. The direction is deliberate and **fail-open**: where the repo's own frozen configuration reruns, a rerun that passes is a pass, because the repo chose that configuration under `C-T2`. | R10 | §11's header line spells `keys_visible=false` as a **literal** while spelling `profile=` as an alternation; §7.4 rule 0 contemplates an *ingested* header that "lacks the assertion", and the trusted-stage behaviour is unstated. | The collector writes `keys_visible=true` and exits non-zero; an ingested `true` fails precondition 2 and raises the `G11` wire. | A chained trusted job may run regardless of the untrusted job's conclusion, so the trusted side needs a defined behaviour rather than an assumption. Admitting `true` **widens** §11's grammar rather than resolving an ambiguity in it, and is reported as a §11 defect. `keys_visible=true` is then the reachable form of rule 0's "header lacks the assertion"; a header *missing* the key is malformed (§4.2) and is never an ingested precondition-2 failure. The two differ in outcome — malformed blocks the landing, a precondition-2 failure lets it proceed under a tripwire review — so the choice is stated rather than left to a reading. |
| R11 | §5.4 says the solo collector "seals `profile=none` honestly" and that preconditions 1 and 2 fail by construction; it does not say what `keys_visible=` is locally, and rule 0's probe names only the pipeline-key variable. | One predicate over signing key material of any kind (§4.2), over the collector and **every** runner invocation, which yields `false` in the untrusted job and `true` on the solo path. Outside `--ci`: `profile=none`, `keys_visible=true`. | Precondition 2 must fail **by construction**, as §5.4 requires. A predicate reading only `SPINE_PIPELINE_KEY` yields `false` on a laptop, where no such variable exists, and would make §5.4's guarantee false while two implementers wrote different bytes into a security-critical field. One rule with two derived answers, not a mode-specific special case — and one answer for the whole job, because the header has one field and a per-runner assertion has nowhere to live. |
| R12 | Nothing says what a crashed run's records are worth. | `status ≠ complete` credits nothing; records are still written as evidence; the AC-coverage clause fails with the rest (§8.5 clause 0). | Otherwise a quick-lane landing — no frozen ids, floor-only G1 — passes vacuously on a `base-collect-failed` file, and a timed-out run satisfies the coverage clause on ids it never finished collecting. |
| R13 | Nothing says whether a malformed file may be partially read. | No partial ingestion, ever — and, by the same argument, no partial `base` section: a failed collection in any runner suppresses the whole body (§7.3). | A truncated `base` section is the one truncation that weakens rather than tightens the gate, and a `base` section holding some of the invocation set's runners and not others is a truncated one that no reader could detect. |
