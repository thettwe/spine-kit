# Codex Adversarial Review of PLAYBOOK.md (v0.8) — model gpt-5.6-sol — 2026-08-26

Second review of the day. Target: working tree (PLAYBOOK.md v0.8, 990 lines, after an internal 59-edit hardening pass). Focus given: re-check the five v0.7 findings against §12's closure map; attack the new machinery (collector + second uid, base=-anchored closure, scratch-clone G10, C-M5/recon=, structural rollback predicate, manifest invariants); check buildability against §10/§11; and ask whether anything in v0.8 is worse than v0.7.

Verdict: needs-attention

No-ship: v0.8 improves the ledger mechanics, but still permits auto-merge on forgeable test outcomes, leaves a straightforward mutable-oracle bypass, and introduces recovery and reconstruction modes that do not preserve the stated trust guarantees.

Findings:
- [critical] C-M4 can be enabled although candidate code can still forge every test outcome (PLAYBOOK.md:806-861)
  The collector protects the result file, not the runner-to-collector stream. Candidate code executes in the runner process and may monkeypatch the reporter or assertions, causing G1 and G6 to record fabricated passes. This residual is disclosed, but the adoption procedure still tells teams to turn C-M4 on after calibration; there is no mechanical capability check that can ever establish runner honesty. C-M4=off adds a human review, but that review is triggered only by the policy setting and receives the same forged gate report, so it does not validate the tests. A prompt-injected agent can therefore satisfy every purported test gate once a team follows the documented enablement path.
  Recommendation: Keep auto-merge mechanically unavailable for in-process runners. Define supported isolation profiles where candidate code cannot influence the authoritative runner/reporter, and require a per-run attestation of such a profile before C-M4 can evaluate as on; otherwise require an explicit human code-and-test-outcome review rather than the generic tripwire review.
- [high] The base-anchored closure still gives greenfield intents an unfrozen oracle (PLAYBOOK.md:297)
  Clause (2) deliberately excludes every branch-created module under expected because it did not exist at base and is classified as code under test. Agent A can therefore create an expected-path helper that computes assertions or golden values, import it only from the approved tests, and modify it during implementation without changing any Spine-Frozen blob. The document acknowledges this residual, but it is the direct greenfield form of the v0.7 mutable-oracle finding, not a narrow edge case; Agent B and forgeable G6 are the only defenses. Frozen-test immutability consequently does not freeze what the tests assert.
  Recommendation: Freeze branch-created expected-path dependencies unless independent static evidence shows they are SUT entry points, such as an inbound import from non-test implementation code in the approval tree. Treat ambiguous or dual-use modules as a closure tripwire requiring protected review.
- [high] The structural rollback predicate permits arbitrary recovery upgrades without the pipeline key (PLAYBOOK.md:815)
  A recovery landing is accepted as a rollback when its manifest cli object matches any ancestor, while its permitted diff includes the manifest and paths listed by the old and new manifests. That condition proves neither that the new manifest equals the ancestor nor that managed files were restored from it. Two reviewers can construct a new manifest that copies an ancestral cli object but supplies arbitrary template, file, parameter, and blob values, then alter protected CI or agent-context paths accordingly. The prose condition that no pipeline key is usable is also not mechanically evidenced. This recreates the exact bypass §12 claims to close: a forward or malicious lifecycle change can masquerade as rollback and land with no trusted stage or pipeline signature.
  Recommendation: Define rollback structurally as a deterministic transformation from a specific ancestor manifest: require all frozen and managed-file records to equal that ancestor except an explicitly enumerated monotone floor union, and require every changed managed path to equal its ancestor blob or the prescribed deletion. Bind the recovery event to that ancestor SHA and reject arbitrary new manifest content.
- [high] Scheduled G10 makes the pre-push reconstruction guarantee non-enforceable (PLAYBOOK.md:619)
  C-M5 permits scheduled:<window>, but the landing seal records only recon=scheduled, omitting the window, deadline, scheduled-run identity, result, and failure disposition. No transition or durable Git-native artifact records an overdue or failed reconstruction, and nothing blocks subsequent landings. Thus a repository may accumulate indefinitely many unproved landings while still carrying valid seals, contradicting the headline and provenance-law claims that reconstruction is proved before each push. This relocates the old post-CAS G10 defect rather than closing it for a supported mode.
  Recommendation: Make inline reconstruction mandatory for valid auto-merged seals. If scheduled mode remains, define it as a degraded non-auto-merge mode and record the exact window plus a Git-native verification or failure event; block further landings after the deadline or first failure.
- [high] Provider-made merges validate a synthetic commit rather than the object that reaches trunk (PLAYBOOK.md:401)
  Configuration (b) explicitly performs no CAS and runs G10 over the locally constructed L, while the provider later creates a different commit. The pre-merge API/body checks are not an atomic guard on trunk, and the actual landing's message, parents, tree, or base can differ through provider behavior or a concurrent trunk update. Detecting the result as unattested after it has entered trunk does not make the auto-merge safe or reconstructible before landing; it is the same irreversible verification ordering the inline G10 change was intended to eliminate.
  Recommendation: Do not support provider-created commits as an auto-merge configuration. Require the trusted stage or a serialized provider queue to push the exact sealed L by CAS, or classify provider-made landings as manual/degraded and require post-creation verification before they become the protected trunk tip.
